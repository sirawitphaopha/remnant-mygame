## 1. 🔴 ลำดับการจัดอันดับ 7 ชั้น — ห้ามสลับ

```
1) เจอที่ต้นชื่อ มาก่อนเจอกลางชื่อ
2) ตำแหน่งที่เจอ ยิ่งต้นยิ่งมาก่อน
3) ของที่ใช้บ่อย (hotIds)
4) ชื่อตามตัวอักษร          ← 🔴 ชั้นนี้คือตัวกันความแรงเรียงข้ามยา
5) รูปแบบยา (FORM_ORDER)
6) ความแรงน้อย → มาก        เฉพาะของชื่อเดียวกัน
7) ชื่อเต็ม
```

### 🔴 บั๊กที่เคยเจอจริง — พิมพ์ `met` แล้ว Metformin ไม่ขึ้นเลย

เพราะเรียงตามความแรงข้ามยาคนละตัว

```
0.2 → 2.5 → 5 → 10 → 12.5 → 100 → 200 │ 250 → 500 (Metformin)
                        ตัดที่ 8 ตัว ┘   ตกขอบ
```

กล่องธรรมดาปล่อยล้นได้อยู่แล้ว แค่**ตั้งระยะบรรทัดไม่ต่ำกว่า 1.5 เท่า**ของขนาดตัวอักษร
🚨 **จุดที่มี `overflow:hidden` + `white-space:nowrap` เสี่ยงที่สุด** เพราะกล่องสูงเท่าบรรทัดพอดี

### 🔴🔴🔴 ไม่ใช่แค่ช่องค้นหา — **ช่องกรอกข้อความไทยทุกช่องในเว็บ**

**พี่กันจับได้ 5 ก.ย. 2569** จากช่อง "ระบุลักษณะเพิ่มเติม…" ในหน้ากรอก

> *"คำว่า ระบุ สระอุ มันโดนตัด · จุดนี้ควรเป็นกฎเดียวกันกับช่องค้นหาไหม"*
> *"ไม่เอา 6 จุด **ปรับช่องให้เป็นระบบเดียวกันทั้งหมด**"*

🔑 **สระล่างโดนตัดด้วยกลไกเดียวกับสระบนเป๊ะ** — `<input>` ตัดทุกอย่างที่ล้นออกนอกตัวเอง
ไม่ได้เลือกว่าล้นบนหรือล้นล่าง · ที่ผ่านมาเห็นแต่ไม้โทหายเพราะคำที่ทดสอบมีแต่สระบน

**เดิมกฎข้อนี้เขียนไว้ในบริบทช่องค้นหาอย่างเดียว** จึงไปแก้แค่ช่องค้นหา
ทั้งที่ช่อง "ระบุ…" · ช่องชื่อยา · ช่องพิมพ์ยืนยันลบถาวร โดนเหมือนกันหมด

### ✅ ตัวกลางมี 2 ตัว เลือกตามหน้าที่ของช่อง

| ช่องแบบไหน | ใช้ตัวไหน | ได้อะไร |
|---|---|---|
| **ช่องค้นหา** | `<SearchBox>` | แว่นขยาย + ปุ่มล้าง + ป้าย "ค้นว่า" + กันสระตัด |
| **ช่องกรอกข้อความทั่วไป** | `<ThaiTextInput>` | กันสระตัด + ขอบโฟกัสมาตรฐาน (ไม่มีแว่นขยาย) |

🚨 **ห้ามเอา `SearchBox` ไปใช้กับช่องกรอกข้อมูล** — ไอคอนแว่นขยายทำให้คนเข้าใจผิดว่า
พิมพ์แล้วระบบจะไปค้นอะไรให้ ทั้งที่เป็นช่องกรอกข้อมูลธรรมดา

### ช่องไหนต้องแปลง ช่องไหนไม่ต้อง

| ชนิดช่อง | ต้องใช้ตัวกลางไหม | เพราะ |
|---|:--:|---|
| ข้อความไทย | ✅ | สระบน/ล่างโดนตัด |
| ชื่อยา (อังกฤษเป็นหลัก) | ✅ | อยู่กล่องเดียวกับช่องไทย ต้องสูงเท่ากัน |
| `type="date"` | ❌ | ไม่มีตัวอักษรไทย |
| `type="tel"` · `inputMode="numeric"` | ❌ | เลขล้วน |
| **`<textarea>`** | ❌ **ถ้าวัดแล้วผ่านเกณฑ์** | ดูหัวข้อถัดไป |

### 🔑 `<textarea>` ไม่ต้องแก้ ถ้าระยะบรรทัดกับขอบในพอ — แต่ต้องวัดก่อน

**วัดของจริงใน ME-DRP 5 ก.ย. 2569** — ทุกช่องได้

```
ขนาดตัวอักษร 15px · ระยะบรรทัด 23.25px (= 1.55 เท่า) · ขอบในบน-ล่าง 12px
```

`<textarea>` ต่างจาก `<input>` ตรงที่ตัดที่**ขอบกล่อง** ไม่ใช่ตัดทุกอย่างที่ล้นบรรทัด
ระยะบรรทัด 1.55 เท่าจึงเผื่อที่ให้สระบน-ล่างพออยู่แล้ว

🚨 **ต้องวัดก่อนสรุปว่าไม่ต้องแก้** — เกณฑ์คือ **ระยะบรรทัด ≥ 1.5 เท่า** และ **ขอบในบน-ล่าง ≥ 10px**
ต่ำกว่านี้เมื่อไหร่ต้องทำตัวกลางของ textarea เพิ่ม

```js
// วางในคอนโซล — บอกว่า textarea ในหน้านี้ผ่านเกณฑ์ไหม
[...document.querySelectorAll('textarea')].map(t => {
  const cs = getComputedStyle(t);
  const เท่า = parseFloat(cs.lineHeight) / parseFloat(cs.fontSize);
  return { เท่า: เท่า.toFixed(2), ขอบใน: cs.paddingTop, ผ่าน: เท่า >= 1.5 && parseFloat(cs.paddingTop) >= 10 };
});
```

### 🔴🔴 กับดักที่ 2 — `overflow:hidden` + `nowrap` ตัดสระโดยไม่ต้องเป็นช่องกรอกเลย

**พี่กันจับได้จากป้าย "— เลือกผู้รายงาน —" ในช่องเลือก** (5 ก.ย. 2569 · *"สระอู"*)
ช่องนั้นไม่ใช่ `<input>` ด้วยซ้ำ เป็นแค่ `<span>` ในปุ่มดรอปดาวที่ทำเอง

**ต้นเหตุ** — กล่องที่มี 3 อย่างนี้พร้อมกันจะสูงเท่าบรรทัดพอดี สระที่ล้นจึงโดนตัด

```
overflow:hidden  +  white-space:nowrap  +  ไม่ได้ตั้ง line-height
```

`line-height: normal` ของ Sarabun ≈ **1.27 เท่า** ซึ่งไม่พอสำหรับสระบน/ล่าง
วัดของจริง: span สูง **19px** ที่ตัวอักษร 15px → พอตั้ง `line-height:1.75` เป็น **26px** สระครบ

### 🔴🔴🔴 สูตรข้างบนผิด — แก้ 23 ก.ย. 2569 (warfarin หน้าต่างสร้างวิธีบริหารใหม่)

**สูตรระยะบรรทัด 1.75 แก้ได้แค่ขอบบนกับขอบล่าง** แต่สระไทยล้นออก **ทั้งสี่ทิศ**
ช่องเลือกที่ตั้ง 1.75 ตามสูตรนี้แล้ว หัว ไ ของคำว่า "ไม่กิน" ยังด้วนอยู่
เจ้าของงานทักสามรอบ *"ไม้มลาย ไ มันโดนตัด อีกเเล้ว"* · *"ยังตัดนี่"* · *"แหกตาดู"*

**วัดของจริงในโครม — Sarabun 15px ตัวอักษรยื่นเกินกล่องของตัวเองกี่จุด** (canvas measureText)

| ยื่นไปทาง | ตัวไหน | กี่จุด |
|---|---|:--:|
| **ซ้าย** | ไ · ใ | 2 |
| **ซ้าย** | โ · ฐ | 1 |
| **ขวา** | ั (ไม้หันอากาศ) | 2 |
| **ขวา** | ้ · ๊ · ์ | 1 |
| **บน** | ็ (ไม้ไต่คู้) | สูง 16 จากขนาด 15 |
| **ล่าง** | ฎ · ฏ · ฐ · ุ · ู | ลงใต้เส้นฐาน 5 |

**ไ ใ โ ขึ้นต้นคำ = ยื่นซ้ายเกินจุดเริ่มตัวหนังสือ**
กล่องตัวหนังสือที่ตั้ง overflow ไว้ (hidden หรือ clip แนวนอนก็ตาม) จะเฉือนหัวทิ้งที่ขอบซ้ายทันที
ระยะบรรทัดเท่าไหร่ก็ช่วยไม่ได้ เพราะไม่ใช่เรื่องความสูง

✅ **ทางแก้ที่ถูก = กฎของเว็บ HCV** (`_hcvnz/components/form/Select.tsx` · เจ้าของงานชี้เอง *"hcv ทำมาเเล้ว"*)

🚨 **เจ้าของงานบอกว่ายังเห็นตัดอยู่ = ยังตัดอยู่** ให้หาว่าวัดพลาดทิศไหน ห้ามเอาตัวเลขไปเถียง

## 12. 🎯 ตัวอักษรในชั้นวาดต้องนั่งตรงกับช่องกรอก

**พี่กันส่งภาพมา 3 รอบ** — *"คำที่ค้น อยู่กลางกรอบยัง"* · *"เราว่ามันอยู่บนๆไป"*

### ต้นเหตุ — สองชั้นจัดกึ่งกลางคนละกลไก

**`<input>` จัดตัวอักษรกึ่งกลางด้วยกลไกของตัวเอง โดยไม่สนระยะบรรทัดที่สั่ง**
ส่วนกล่องธรรมดาเคารพระยะบรรทัด → เส้นฐานของสองชั้นอยู่คนละที่

⚠️ **วัดกล่องแล้วจะบอกว่าถูก** — กล่องตัวอักษรอยู่กลางกรอบเป๊ะ เยื้อง 0 จุด
สิ่งที่เยื้องคือ **ตัวอักษรข้างในกล่อง** ซึ่งการวัดกรอบจับไม่ได้

```js
// ❌ ผิด — ระยะบรรทัด 1.75 เท่า ทำให้เส้นฐานคนละที่กับช่องกรอก
<span style={{ font: '400 13px/1.75 Sarabun' }}>

// ✅ ถูก — ระยะบรรทัดเท่ากับ "ความสูงในกรอบ" (ความสูงกรอบ ลบขอบบนล่าง)
<span style={{ font: '400 13px/1.75 Sarabun', lineHeight: (h - 2) + 'px' }}>
```

ยังเหลือที่ว่างบนล่างข้างละ 7 จุดให้วรรณยุกต์เท่าเดิม เพราะชั้นวาดยังยื่นออกนอกกรอบด้วย
`top:-7px;bottom:-7px`

🔑 **ตรวจด้วยไอคอนที่อยู่ในช่องเดียวกัน** — แว่นขยายจัดกึ่งกลางด้วย `top:50%;translateY(-50%)`
ซึ่งกลางจริงเสมอ **ตัวอักษรต้องอยู่ระดับเดียวกับไอคอน** ถ้าเยื้องคือผิด
เร็วและเชื่อได้กว่าการวัดตัวเลข

| เนื้อในเปลี่ยนความสูง | **วัดใหม่ทุกครั้ง** — พิมพ์คำใหม่ผลลัพธ์สั้นยาวไม่เท่ากัน |

🚨 **ห้ามตัดสินจากตำแหน่งอย่างเดียว** เช่นเช็คว่า "อยู่ครึ่งล่างของจอไหม"
เมนูสั้นที่อยู่ครึ่งล่างก็กางลงได้สบาย ส่วนเมนูยาวที่อยู่เหนือครึ่งจอนิดเดียวกลับล้น
**ต้องวัดความสูงจริงของกรอบเทียบกับที่ว่างจริง**

🔗 วิธีทำกับโค้ดตัวอย่างอยู่ในสกิล **`web-craft` ข้อ 6.25** — ใช้ตัวกลางตัวเดียวกับปฏิทินและดรอปดาวน์

## 15. ลูกศรเลื่อน กรอบต้องเลื่อนตาม

กรอบผลค้นหาสูงราว 290px เห็นราว 5 แถว
กดลูกศรลงไปแถวที่ 6 ตัวที่ถูกเลือกจะซ่อนใต้ขอบกรอบ **ผู้ใช้กดต่อแบบตาบอด**

```jsx
componentDidUpdate(prevProps, prevState) {
  if (prevState.hi !== this.state.hi && this.hiRef.current) {
    this.hiRef.current.scrollIntoView({ block: 'nearest' });
  }
}
```

`block:'nearest'` = เลื่อนน้อยที่สุดเท่าที่จำเป็น แถวที่เห็นอยู่แล้วไม่ขยับ

🚨 **ทำใน `componentDidUpdate` ไม่ใช่ ref callback** เพราะ ref ถูกเรียกทุกครั้งที่วาดจอ
จะดึงกรอบกลับตอนผู้ใช้เลื่อนดูเองด้วยเมาส์

## 16. ลูกศรวนรอบ

```js
export function moveHi(current, delta, total) {
  if (!total) return -1;
  if (current < 0) return delta > 0 ? 0 : total - 1;  // ยังไม่ชี้ · กดขึ้น = ไปตัวสุดท้าย
  let next = current + delta;
  if (next < 0) next = total - 1;
  if (next >= total) next = 0;
  return next;
}
```

## 18. 🔴🔴🔴 คำไทยสองคำที่ตาเห็นเหมือนกันเป๊ะ แต่ระบบมองเป็นคนละคำ

**ความรู้ภาษาไทยที่ไม่มีที่ไหนในสกิลเลย** — เจอที่เว็บ listless ซึ่งใช้ Google Sheet

### เรื่องคืออะไร

คำว่า **`กี่`** เขียนได้สองแบบ ขึ้นกับว่าวางเครื่องหมายไหนก่อน

```
แบบ A   ก + สระอี + ไม้เอก
แบบ B   ก + ไม้เอก + สระอี
```

**ตาคนมองเห็นเหมือนกันทุกประการ** วางซ้อนกันแล้วแยกไม่ออก
แต่คอมพิวเตอร์เก็บเป็นข้อมูลคนละชุด **จึงเป็นคนละคำสำหรับระบบ**

### ผลที่ตามมา

| เกิดอะไร | อาการ |
|---|---|
| ค้นหา | พิมพ์แบบ A หาแบบ B ไม่เจอ **ทั้งที่คำอยู่ตรงนั้น** |
| นับจำนวน | คนเดียวกันถูกนับเป็นสองคน |
| จับกลุ่ม | ข้อมูลของคนเดียวกันแตกเป็นสองก้อน |
| เทียบว่าซ้ำไหม | ระบบบอกว่าไม่ซ้ำ ทั้งที่ซ้ำ |

### 🚨🔴 วิธีแก้มาตรฐานสากลใช้ไม่ได้กับภาษาไทย

> *"`normalize('NFC')` **does not fix it** — verified · Unicode has no canonical order for Thai marks"*

คำสั่ง `normalize('NFC')` เป็นวิธีที่โปรแกรมเมอร์ทั่วโลกใช้จัดระเบียบตัวอักษรให้เป็นแบบมาตรฐาน
**แต่มาตรฐาน Unicode ไม่ได้กำหนดลำดับสำหรับเครื่องหมายภาษาไทย** — พิสูจน์แล้วว่าไม่แก้ให้

### วิธีที่ต้องทำ — เรียงเครื่องหมายเอง

ทำ **กุญแจสำหรับเทียบ** ที่จัดเรียงสระกับวรรณยุกต์ของแต่ละพยัญชนะให้เป็นลำดับเดียวกันเสมอ
พร้อมล้างของที่มองไม่เห็นออกด้วย (อักขระความกว้างศูนย์ · เครื่องหมายลำดับไบต์ · ยัติภังค์อ่อน ·
ช่องว่างชนิดแปลก · ช่องว่างซ้อนหลายตัว)

🚨🔴 **กุญแจนี้ใช้เทียบอย่างเดียว ห้ามเอาไปแสดงบนจอ และห้ามเขียนกลับลงฐานเด็ดขาด**
เพราะมันคือรูปแบบที่จัดใหม่เพื่อเทียบ ไม่ใช่ข้อความที่ผู้ใช้พิมพ์มา

```
เก็บลงฐาน   ← ข้อความจริงที่ผู้ใช้พิมพ์ (ไม่แตะ)
แสดงบนจอ    ← ข้อความจริง
เทียบ/ค้น/นับ ← กุญแจที่จัดเรียงแล้ว
```

### 🔑 ทำความสะอาดข้อความที่ "ตอนรับเข้า" ไม่ใช่ "ตอนแสดงผล"

ถ้าล้างตอนแสดงผล ข้อมูลสกปรกยังนอนอยู่ในฐาน แล้วทุกที่ที่หยิบไปใช้ต้องล้างเองซ้ำ ๆ
**ล้างที่ประตูทางเข้าครั้งเดียว ข้างในสะอาดหมด**
