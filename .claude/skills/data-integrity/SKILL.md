## 🔴 ทำไมกลุ่มนี้อันตรายกว่าบั๊กทั่วไป

# ✍️ การเขียนลงฐาน

## ①🔴🔴 คำสั่งอัปเดตแบบรวม ล้างช่องที่ไม่ได้ส่งเป็นค่าว่าง

**เกิดจริงที่เว็บยาคืน** — เดิมใช้กับตารางที่มี 6 ช่อง พอย้ายมาใช้กับตารางที่มียี่สิบกว่าช่อง
**ช่องที่ไม่ได้ส่งไปโดนล้างทิ้งหมด**

```js
// ❌ อันตรายกับตารางคอลัมน์เยอะ — ช่องที่ไม่ได้ส่ง กลายเป็นค่าว่าง
await db.from('drugs').upsert(rows);

// ✅ แก้รายแถวด้วยคำสั่งแก้ไข ส่งเฉพาะช่องที่ตั้งใจแก้
await db.from('drugs').update(patch).eq('id', id);
```

🚨 **คำสั่งแบบรวมใช้ได้เฉพาะตอนเพิ่มแถวใหม่ หรือตารางที่ส่งครบทุกช่องจริง ๆ**

⚠️ **ตระกูลเดียวกับบั๊กส่งหลายแถวพร้อมกัน** — ตัวกลางจะรวมรายชื่อช่องจากทุกแถวเป็นชุดเดียว
แถวไหนไม่มีช่องนั้นถูกเติมค่าว่าง **ถ้าแถวมีชุดช่องไม่เท่ากันต้องแยกกลุ่มก่อนเสมอ**

## ②🚨 รายการคอลัมน์ที่ส่งไม่ครบ = แก้แล้วไม่บันทึก แบบไม่มีข้อผิดพลาด

> *"รายการคอลัมน์ไม่ครบ = แก้จากหน้าคลังยาแล้วค่าไม่ถูกบันทึกแบบเงียบ ๆ ไม่มีข้อผิดพลาด
>  **เป็นจุดที่พลาดง่ายที่สุดเวลาเพิ่มคอลัมน์ใหม่**"*

🚨 **เพิ่มช่องใหม่ในฐานเมื่อไหร่ ต้องไล่เติมให้ครบ 3 ที่พร้อมกัน**

```
① ตารางในฐาน   ② รายการคอลัมน์ที่โค้ดส่งขึ้นไป   ③ ช่องกรอกบนหน้าจอ
```

ขาดข้อ ② = หน้าจอมีช่องให้กรอก กดบันทึกแล้วขึ้นว่าสำเร็จ **แต่ค่าไม่เคยไปถึงฐาน**

## ③🔴🔴 ค่าที่บันทึกลงฐาน ห้ามเป็นข้อความเดียวกับที่โชว์บนจอ

```js
// ✅ แยกกัน — ป้ายที่โชว์เปลี่ยนได้ตลอด ค่าที่บันทึกห้ามขยับ
{ key: 'wrong_dose', label: 'ขนาดยาไม่ถูกต้อง (Wrong dose)' }
```

**ถ้าบันทึกป้ายลงฐาน** วันที่แก้ข้อความบนจอให้อ่านง่ายขึ้น
**ข้อมูลเก่าทั้งหมดจะถูกนับเป็นคนละหมวดทันที** ตัวเลขสรุปย้อนหลังแตกโดยไม่มีใครรู้

## ④🔴🔴 ซากฟังก์ชันเก่าทับถมกันในฐาน

**เจอจริงที่เว็บยาคืน — ฟังก์ชันชื่อเดียวกันมี 4 ตัวพร้อมกันในฐาน**

```
เพิ่มพารามิเตอร์ทีละตัว → ฐานถือว่าเป็นคนละฟังก์ชัน → คำสั่งสร้างทับไม่ทับตัวเดิม
→ เว็บเรียกไปโดนตัวเก่า → แก้โค้ดเท่าไหร่ก็ไม่เปลี่ยน
```

🚨 **แก้ฟังก์ชันในฐานแล้วต้องไล่ดูว่าเหลือกี่ตัว และลบตัวเก่าทิ้งให้หมด**
🔑 **อาการที่บอกว่าเจอบั๊กนี้** — แก้แล้วไม่เปลี่ยน ทั้งที่โค้ดถูกและรันคำสั่งสำเร็จ

# 🗑 การลบและการกู้คืน

## ⑤🔴 ตัวลบต้องตอบว่าโดนจริงกี่แถว ไม่ใช่แค่ว่าไม่มีข้อผิดพลาด

```ts
// ✅ คืน true เฉพาะเมื่อมีแถวถูกแตะจริง
export async function กู้คืน(id: string): Promise<boolean> {
  const d = await ส่งหลังบ้าน<{ restored?: boolean }>("/api/trash", "POST", { id });
  return !!d.restored;     // เครื่องอื่นลบถาวรไปแล้ว → โดน 0 แถว → false ไม่หลอกว่าสำเร็จ
}
```

**"ไม่มีข้อผิดพลาด" ไม่ได้แปลว่าลบโดน** — แถวอาจถูกลบไปแล้วจากอีกเครื่อง
ถ้าไม่นับแถว หน้าจอจะขึ้นว่า "ย้ายไปถังขยะแล้ว" ทั้งที่ไม่มีอะไรเกิดขึ้น

## ⑥🔴 สถานะถังขยะเปลี่ยนได้ทางเดียว คือปุ่มลบกับปุ่มกู้คืน

**ลำดับที่ทำให้ของที่ลบแล้วฟื้นขึ้นมาเอง**

```
เครื่อง A เปิดหน้าแก้ไขค้างไว้  →  เครื่อง B ลบลงถังขยะ  →  เครื่อง A กดบันทึก
→ ข้อมูลที่ A ส่งไปมีสถานะ "ยังไม่ลบ" ติดไปด้วย  →  ของที่ลบแล้วกลับมา
```

🚨 **เส้นทางบันทึกกับแก้ไข ห้ามแตะช่องสถานะการลบเด็ดขาด** ต่อให้ส่งมาก็ต้องตัดทิ้ง

# ✏️ การแก้ข้อมูลที่คนอื่นอาจกำลังใช้อยู่

## ⑦🔴🔴 เขียนทับข้อมูลจริงอัตโนมัติ ต้องมีด่านครบ 3 ชั้นต่อหนึ่งช่อง

**ยกมาจากระบบที่เขียนค่าลงตารางจริงให้อัตโนมัติ** — ทั้งสามชั้นต้องผ่านพร้อมกัน

| ชั้น | ตรวจอะไร | กันอะไร |
|:--:|---|---|
| 1 | ช่องนี้อยู่ในรายการที่อนุญาตให้แก้ไหม | เขียนโดนช่องที่ห้ามแตะ |
| 2 | แถวนี้อยู่ในช่วงที่มีจริงไหม | เขียนตกขอบ หรือทับหัวตาราง |
| 3 | **ค่าปัจจุบันยังเท่ากับค่าที่ฝั่งจอเห็นตอนสั่งไหม** | **ของขยับไปแล้วระหว่างทาง** |

🔑 **ชั้นที่ 3 คือชั้นที่ทำให้ยิงใส่ข้อมูลที่อาจถูกคนอื่นแก้ไปแล้วได้อย่างปลอดภัย**
ไม่มีชั้นนี้ = เขียนทับงานคนอื่นเงียบ ๆ

## ⑧🔴 ข้อมูลสดจากเครื่องอื่น ห้ามทับสิ่งที่ผู้ใช้กำลังแก้อยู่

```js
if (editMode) return;    // กำลังเปิดหน้าแก้ไขอยู่ — ห้ามเอาข้อมูลใหม่มาทับ
```

**ไม่มีบรรทัดนี้ = พิมพ์อยู่ดี ๆ ช่องกรอกเด้งกลับเป็นค่าเก่า** ผู้ใช้ไม่รู้ว่าเกิดอะไร

## ⑨🔴 แก้ข้อมูลให้ผู้ใช้ ต้องเก็บค่าเดิมไว้และแสดงให้เห็นว่าแก้แล้ว

ระบบที่เติมหรือแก้ค่าให้อัตโนมัติ **ต้องเก็บของเดิมไว้เสมอ** และขึ้นป้ายบอกว่าถูกแก้
🚨 **ห้ามเขียนทับของเดิมทิ้ง** เพราะพอผู้ใช้ทักว่าค่าผิด จะไม่มีอะไรให้ย้อนดูว่าเดิมเป็นอะไร

# 🙈 ค่าที่ระบบเปลี่ยนเองโดยผู้ใช้ไม่รู้

## ⑩🔴🔴 การแอบตัดค่าที่เกินเพดาน อันตรายกว่าไม่กั้นเลย

**พี่กันเจอเอง** — *"เราเพิ่งรู้ว่า เงินมันไม่เกิน 1 แสนเหรอ ทำไมแฮะ"*

```js
// ❌ ตัดให้เงียบ ๆ โดยไม่บอกอะไร — ผู้ใช้กรอก 250000 ได้ 100000 แล้วไม่รู้ตัว
const qty = Math.min(MAX_QTY, n);

// ✅ กั้นแล้วบอกให้เห็น
if (n > MAX_QTY) { แจ้ง('จำนวนสูงสุดคือ ' + MAX_QTY.toLocaleString()); return; }
```

🚨 **กติกาที่มีอยู่ในระบบ ต้องเขียนให้เห็นบนหน้าจอ** ไม่ใช่ซ่อนไว้ในโค้ด
ผู้ใช้ที่ไม่รู้ว่ามีเพดาน จะรายงานตัวเลขที่ถูกตัดไปแล้วโดยเชื่อว่าถูกต้อง

## ⑪ ค่าที่คำนวณไว้แต่ไม่มีใครวาด = ฟีเจอร์ที่มีแต่ใช้ไม่ได้

**ตรงกันข้ามกับข้อ ⑫ แต่มาจากรากเดียวกัน** — ของที่มีอยู่แต่ไม่ได้ต่อสาย
ไม่มีข้อความผิดพลาด ไม่มีอะไรในบันทึกของเบราว์เซอร์ **หน้าเว็บดูปกติทุกอย่าง**

## ⑫🔴🔴 ช่องในฐานที่มีข้อมูลอยู่แล้วแต่ไม่มีโค้ดหยิบมาใช้เลย

**เจอ 3 รอบในไฟล์เดียวที่เว็บยาคืน** — ช่องชื่อการค้ามีข้อมูล 37 จาก 417 แถว
ช่องรูปแบบการออกฤทธิ์มีข้อมูล 12 แถว **ไม่มีโค้ดตรงไหนหยิบมาแสดงเลยสักจุด**

🚨 **ก่อนบอกว่าฟีเจอร์ครบ ให้ไล่ทุกช่องในตารางว่ามีใครใช้จริงไหม**

```sql
-- นับว่าช่องไหนมีข้อมูลบ้าง แล้วเอาไปเทียบกับที่โค้ดหยิบใช้จริง
select count(brand) as มีชื่อการค้า, count(release) as มีรูปแบบออกฤทธิ์ from drugs;
```

# 🧪 ข้อมูลจริงกับข้อมูลสาธิต

## ⑬🔴 โหมดดูตัวอย่างต้องเป็นของปลอมทั้งหมด ทุกหน้า

**เดิมกดแท็บคลังยาในโหมดตัวอย่างแล้วโหลดยาจริง 417 ตัวพร้อมราคามาโชว์**
เพราะตัวโหลดคลังกับตัวโหลดราคา **ไม่รู้จักโหมดนี้เลย**

🚨 **โหมดสาธิตต้องดักที่จุดรวมของการดึงข้อมูล ไม่ใช่ไล่ดักทีละหน้า**
ไล่ทีละหน้าจะลืมหน้าที่เพิ่งเพิ่มเสมอ

## ⑭🔴 สำรองข้อมูลก่อนแตะฐานทุกครั้ง และโฟลเดอร์สำรองห้ามขึ้นระบบเก็บโค้ด

```bash
echo "backups/" >> .gitignore     # ทำก่อนสำรองครั้งแรก
```

**ไฟล์สำรองคือข้อมูลจริงทั้งก้อน** หลุดขึ้นที่สาธารณะแล้วเรียกคืนไม่ได้

# 🔄 ข้อมูลที่วิ่งมาจากเครื่องอื่น

## ⑮🔴 อัปเดตสดข้ามเครื่อง ต้องใช้ "ลายเซ็นข้อมูล" ไม่ใช่แค่นับแถว

**การนับแถวจับได้แค่ "เพิ่ม" กับ "ลบ"**
จับ "แก้จำนวน" หรือ "เปลี่ยนสถานะ" ไม่ได้เลย เพราะจำนวนแถวเท่าเดิม

```sql
-- ต้องมีร่องรอยเวลาในฐาน + ตัวดักที่อัปเดตให้อัตโนมัติ
alter table xxx add column updated_at timestamptz default now();
create trigger xxx_touch before update on xxx
  for each row execute function moddatetime(updated_at);
```

ลายเซ็น = จำนวนแถว + เวลาที่แก้ล่าสุด **เปลี่ยนเมื่อไหร่ก็รู้ว่ามีอะไรขยับ**

## ⑯🔴 ต้องแยกให้ออกว่าใครเป็นคนแก้ — ตัวเองหรือเครื่องอื่น

**ไม่แยก = กดบันทึกเองแล้วเด้งข้อความ "มีข้อมูลใหม่จากเครื่องอื่น" ทุกครั้ง**
ผู้ใช้จะเลิกอ่านข้อความนั้นภายในวันเดียว แล้ววันที่มีของจากเครื่องอื่นจริงก็จะไม่มีใครสนใจ

🚨 **เวลาที่เผื่อไว้ต้องมากกว่าคาบของตัวจับเวลาเสมอ**
ตัวจับเวลาเดิน 30 วินาที แต่เผื่อไว้ 20 = จับไม่ทันบางรอบ **ต้องเผื่อ 45**

# 🗄 การแก้โครงตารางที่คนอื่นใช้อยู่

## ⑰🔴 ห้ามเพิ่มคอลัมน์ในตารางที่มีคนใช้งานปลายทาง

**เจอจริง** — ตารางรายงานที่ครูเอาไปทำงานต่อ **การเพิ่มคอลัมน์ที่ 23 จะพังสิ่งที่เขาทำอยู่**

> *"นั่นเป็นการตัดสินใจเชิงผลิตภัณฑ์ ไม่ใช่รายละเอียดการเขียนโค้ด"*

🚨 **ของที่ต้องเก็บเพิ่ม ให้ไปอยู่ตารางแยก** แล้วโยงกลับด้วยรหัส
ตารางแยกนั้นยังใช้ย้อนคืนการแก้ได้ด้วย — เล่นกลับหลังทีละรายการ

⚠️ **ต่างจากตารางที่เว็บเราเป็นเจ้าของเอง** ตรงนั้นเพิ่มคอลัมน์ได้ตามปกติ
เส้นแบ่งคือ **มีใครนอกทีมอ่านตารางนี้ตรง ๆ อยู่ไหม**

## ⑱🔴 กฎการนับตัวตนต้องมีชุดเดียวในระบบ

**ตัวนับ "มีกี่คน" ต้องมีที่เดียว ห้ามเขียนซ้ำเป็นชุดที่สอง**

```
ไฟล์ A นับแบบหนึ่ง  ·  ไฟล์ B นับอีกแบบ
→ ป้ายสรุปกับกราฟบอกตัวเลขไม่ตรงกัน และไม่มีใครรู้ว่าอันไหนถูก
```

🚨 **ไฟล์อื่นต้องเรียกตัวกลางตัวนั้น ห้ามคัดลอกตรรกะไปวาง**
ตระกูลเดียวกับกฎ "อะไรที่คล้ายกันต้องรวมเป็นตัวกลางตัวเดียว"

## ✅ เช็คก่อนบอกว่าเส้นทางบันทึกปลอดภัย

- [ ] คำสั่งเขียนใช้ตัวที่ไม่ล้างช่องที่ไม่ได้ส่ง (ดูข้อ ①)
- [ ] เพิ่มช่องใหม่แล้วเติมครบทั้ง 3 ที่ — ฐาน · รายการคอลัมน์ที่ส่ง · หน้าจอ
- [ ] ค่าที่บันทึกแยกจากป้ายที่โชว์
- [ ] ตัวลบและตัวกู้คืนคืนค่าตามจำนวนแถวที่โดนจริง
- [ ] เส้นทางบันทึกไม่แตะช่องสถานะการลบ
- [ ] ข้อมูลสดไม่ทับหน้าที่กำลังแก้อยู่
- [ ] ไม่มีการตัดค่าเงียบ ๆ เหลือแต่การกั้นที่บอกผู้ใช้
- [ ] ฟังก์ชันในฐานเหลือตัวเดียวต่อหนึ่งชื่อ
- [ ] ทุกช่องในตารางมีคนหยิบไปใช้จริง
- [ ] อัปเดตสดใช้ลายเซ็นข้อมูล ไม่ใช่นับแถว และแยกออกว่าใครเป็นคนแก้
- [ ] ไม่ได้เพิ่มคอลัมน์ในตารางที่มีคนใช้งานปลายทาง
- [ ] กฎการนับตัวตนมีชุดเดียวในระบบ
