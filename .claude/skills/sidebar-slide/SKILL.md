# กดย่อขยายแถบเมนูแล้วต้องลื่น — กฎกลาง ใช้ได้ทุกโปรเจกต์

> 🗺️ เปิดคู่กับ — **`web-craft`** เรื่องตารางจริงและหน้าตาตาราง · **`testing-proof`** เรื่องพิสูจน์ก่อนบอกว่าเสร็จ
>
> 📄 **โค้ดจริงยกไปวางได้เลยอยู่ที่ `CODE.md` ข้าง ๆ ไฟล์นี้**
> อ่าน `SKILL.md` (กฎ) ก่อน เลือกเงื่อนไขให้ถูก แล้วเปิด `CODE.md` ตอนลงมือ

> **ตั้งขึ้น 2 ตุลาคม 2569 ตามที่พี่กันสั่งเอง**
> *"ระบบเลื่อนของทั้งหน้าบริหาร เเละหน้าคลังยาที่ตอนนี้ลื่นเเล้ว สะกัดออกมาเป็นสกิลหน่อย
>  ครั้งหน้าจะได้ไปเอาระบบนั้นมาเลย เเต่มันจะมีสองเงื่อนไขเนอะ เพราะสองหน้านี้ไม่เหมือนกัน"*
> *"ระบบ optimize ด้วยนะ ที่เธอให้เรนเด้อเฉพาะจุด"*

## 0 · ทำไมกดแล้วกระตุก — ต้นเหตุที่วัดได้จริง

โครงหน้าแบบที่ใช้กันในเว็บพี่กัน — แถบเมนูซ้ายพับได้ พื้นที่เนื้อหาเลื่อนตามด้วย
`transition: margin-inline-start .2s ease` และตั้งตัวแปร `--nav-w` (เช่น 200 กับ 56) ให้หน้าข้างในรู้ว่าแถบเมนูกว้างเท่าไร

ตลอด 0.2 วินาทีนั้น **อะไรในหน้าที่ขึ้นกับความกว้างที่เปลี่ยน เบราว์เซอร์ต้องคำนวณใหม่ทุกเฟรม**

| ต้นเหตุ | เกิดอะไร | วัดได้ (จอ 1366 × 577) |
|---|---|---|
| ① ตัวแปรที่สืบทอดลงทั้งหน้า (`--nav-w`) เปลี่ยนค่า | คิดสไตล์ใหม่ทุกชิ้นข้างใต้ | หน้าราว 9,700 ชิ้น = 45–54 ms ตอนกด |
| ② **ตารางเปลี่ยนความกว้างทุกเฟรม** | คำนวณและวาดใหม่ **ทุกแถวที่อยู่ในหน้า** ถึงแถวนั้นจะอยู่นอกจอ | 400 แถว = เฟรมยาว 33–66 ms · ซ่อนแถวหมด = 16.7 ms ลื่น |
| ③ ความกว้างเปลี่ยนทันทีแต่ขอบซ้ายค่อย ๆ เลื่อน | ขอบขวาเลยจอหรือเว้นช่องระหว่างเลื่อน แถบเลื่อนแนวนอนแวบ | ต่างเท่าความกว้างที่แถบเมนูหด (144 จุด) |

ที่มาของตัวเลข — การคิดสไตล์ (45–54 · 48 เหลือ 3) วัดในโครม · ความยาวเฟรม (33–66 · 16.7) วัดในเบราว์เซอร์ของแอป
ซึ่งใช้ตัววาดเดียวกับโครม ตอนแท็บโครมถูกบัง ขนาดจอตั้งเท่าเครื่องพี่กัน · ผลสุดท้ายพี่กันดูเองในโครมว่าลื่น

🔴🔴 **ตัวถ่วงหลักคือ จำนวนแถวในหน้า × ความกว้างตารางที่เปลี่ยน ไม่ใช่ของในช่อง**
พิสูจน์แล้วด้วยการทดลองชั่วคราว — ซ่อนของในช่องทุกช่องก็ยังช้า · ล็อกความกว้างตารางไว้ลื่นทันที · ลดเหลือครึ่งตาราง ช้าลดลงครึ่งหนึ่ง

## 1 · 🔴 เลือกเงื่อนไขก่อนลงมือ — ตารางของหน้านี้แบบไหน

| | **ก · ตารางกว้างเกินจอ** | **ข · ตารางพอดีจอ มีคอลัมน์ยืด** |
|---|---|---|
| ตัวอย่างที่ทำแล้วลื่น | หน้าคลังยา warfarin | หน้าวิธีบริหารยา warfarin |
| ดูยังไง | ทุกคอลัมน์ล็อกความกว้าง รวมแล้วกว้างกว่าพื้นที่เนื้อหา การ์ดมีความกว้างขั้นต่ำ | มีคอลัมน์ที่ไม่ล็อกความกว้าง ยืดรับที่ว่าง (เช่นข้อความยาว) |
| ตอนพับแถบเมนู ความกว้างตาราง | **ไม่เปลี่ยน** (หรือเปลี่ยนนิดเดียวครั้งเดียวตอนกด) | **ต้องเปลี่ยนตาม** ทุกเฟรม |
| ทำอะไร | ข้อ 2 | ข้อ 3 ครบทั้ง 3 ชิ้น |

🚨 ห้ามเอาวิธีของเงื่อนไข ก ไปใช้กับตารางเงื่อนไข ข ตรง ๆ
ตารางพอดีจอถ้าอ่าน `--nav-w` ตรง ๆ ความกว้างจะเปลี่ยนทีเดียวตอนกด ตอนกางแถบเมนูขอบขวาจะเว้นช่องว่างระหว่างเลื่อน (ต้นเหตุ ③)

## 2 · เงื่อนไข ก — ตารางกว้างเกินจอ (แบบหน้าคลังยา)

ความกว้างตารางไม่ต้องเปลี่ยน เบราว์เซอร์จึงแค่ **เลื่อนตารางไปทั้งก้อน** ไม่ต้องคำนวณแถวใหม่ วาดครบทุกแถวได้

| ชิ้น | ทำยังไง |
|---|---|
| การ์ด | `width: max(<ขั้นต่ำ>px, calc(100vw - var(--nav-w) - <ระยะขอบสองข้าง>px))` อ่าน `--nav-w` ตรง ๆ ได้ ความกว้างสุดท้ายมาครั้งเดียวตอนกด |
| ตาราง | `table-layout: fixed` + ความกว้างทุกคอลัมน์อยู่ใน `<colgroup>` ไม่มีคอลัมน์ยืด |
| ตารางแยกชั้นวาด | `transform: translateZ(0); will-change: transform` เลื่อนทั้งก้อนโดยไม่ต้องวาดใหม่ |
| ชิ้นที่ตรึงซ้ายขวา (หัวเรื่อง แถบค้นหา) ที่คิดตำแหน่งจากแถบเมนู | ใส่ `transition: inset-inline-start .2s ease, width .2s ease` จังหวะเดียวกับแถบเมนู ไม่งั้นกระโดดก่อนของอื่น |

🔑 ขั้นต่ำของการ์ดต้องมากกว่าพื้นที่เนื้อหาตอนกางแถบเมนูบนจอที่ใช้จริง ตารางจึงล้นขวาอยู่แล้ว ไม่มีใครเห็นขอบขวาขยับ
บนจอ 1366 การ์ดคลังยาขั้นต่ำ 1270 ตอนกาง 1270 ตอนพับ 1274 ต่างกันแค่ 4 จุด

## 3 · เงื่อนไข ข — ตารางพอดีจอ มีคอลัมน์ยืด (แบบหน้าวิธีบริหารยา) ต้องทำครบ 3 ชิ้น

### ① ตัวแปรความกว้างแถบเมนูแบบค่อย ๆ เปลี่ยน — ให้ขอบขวานิ่ง

ประกาศตัวแปรชนิดความยาวแบบ **ไม่สืบทอด** ไว้ในไฟล์ธีม แล้วทุกชิ้นที่คิดตำแหน่งหรือความกว้างจากแถบเมนู
(การ์ด หัวเรื่อง แถวแท็บ แถบเครื่องมือ) ตั้งค่ากับจังหวะ **ที่ตัวเอง** แล้วอ่านตัวนี้แทน `--nav-w`

- ทุกชิ้นเลื่อนพร้อมขอบซ้ายเป็นก้อนเดียว ขอบขวาอยู่กับที่ตลอดการเลื่อน
- 🔴 **ห้ามตั้งเป็นแบบสืบทอดแล้วตั้งที่กล่องนอกสุด** เบราว์เซอร์ต้องคิดสไตล์ใหม่ทั้งหน้าทุกเฟรม 50–80 ms ต่อเฟรม
- 🔴 ห้ามใส่ transition ของ width หรือ inset ซ้อนให้ชิ้นที่อ่านตัวนี้แล้ว

### ② วาดเฉพาะแถวที่เห็น — ตัวแก้หลัก (*"เรนเดอร์เเค่ที่เห็นสิ"* พี่กันสั่ง 2 ต.ค. 2569)

ตารางต้องเลื่อนอยู่ในกรอบของตัวเอง (กล่องครอบมี `overflow-y: auto`)

| กฎ | ทำไม |
|---|---|
| วาดแถวที่อยู่ในกรอบ เผื่อบนล่างอย่างละหนึ่งจอ (อย่างน้อย 400 จุด) | เลื่อนปกติไม่เห็นขอบที่ยังไม่ได้วาด |
| ที่เหลือแทนด้วย **แถวเว้นที่** บน 1 แถว ล่าง 1 แถว สูงเท่าแถวจริงที่มันแทน | แถบเลื่อนยาวเท่าเดิม ตำแหน่งเลื่อนตรงเดิม |
| ความสูงแถวจริงวัดจากจอ จำไว้ตามรหัสแถว แถวที่ยังไม่เคยวาดใช้ค่าเฉลี่ย | แถวสูงไม่เท่ากัน (ข้อความตัดสองบรรทัด) |
| เก็บความสูงที่วัดใหม่หลังขนาดตารางนิ่ง 80 ms | ระหว่างเลื่อนแถบเมนูข้อความตัดบรรทัดใหม่ทุกเฟรม เก็บทันที = วาดหน้าใหม่ทุกเฟรม |
| ตำแหน่งเลื่อนเก็บเป็นขั้นละ 100 จุด | เลื่อนทีละนิดไม่ต้องวาดหน้าใหม่ |
| แถวเว้นที่ ไม่มีระยะใน เส้น เงา สีตอนชี้ · `pointer-events: none` · `overflow-anchor: none` | ความสูงตรงเป๊ะ · เบราว์เซอร์ยึดแถวจริงตอนรักษาตำแหน่งเลื่อน |
| แถวจริงทุกแถวมี `data-k` เป็นรหัสแถว | ตัววัดความสูงอ่านจากตรงนี้ |
| 🔴 ตัวนับ *"กำลังแสดง N แถว"* กับปุ่มแสดงทั้งหมด นับจากรายการเต็มเหมือนเดิม | ห้ามนับจากแถวที่วาด (สกิล `data-integrity` ห้ามตัดเงียบ) |

ผลที่หน้าวิธีบริหารยา — 400 แถว เหลืออยู่ในหน้าจริง 19–26 แถว (กรอบสูง 315 จุด) พี่กันดูเองในโครมว่าลื่นแล้ว
เทสเลื่อนกลางตารางและเลื่อนขึ้นไปหาแถวที่ยังไม่เคยวาด แถวบนสุดที่เห็นอยู่ที่เดิมทั้งก่อนและหลังตัววัดความสูงทำงาน

⚠️ ข้อจำกัดที่ต้องรู้ — ค้นด้วย Ctrl+F ไม่เจอแถวที่ยังไม่ได้วาด (ใช้ช่องค้นหาของหน้าแทน) ·
ลากแถบเลื่อนไกล ๆ ทีเดียวอาจเห็นช่องว่างแวบหนึ่งเฟรมก่อนแถววาดตามทัน

🔴 ตัวตรวจโค้ดของ React ฟ้อง *"Cannot access refs during render"* ถ้าตั้งชื่อตัวผูกขึ้นต้นด้วย `ref`
หรือใช้ค่าจากก้อนเดียวกับตัวผูก ต้องแยกค่าออกมาเป็นตัวแปรทีละตัว (เจอจริง 10 จุด 2 ต.ค. 2569)

### ③ ตัวกันตารางคิดสไตล์ใหม่ — ตั้ง `--nav-w` ของตารางเป็น 0

`--nav-w` สืบทอดลงมาจากโครงหน้า เปลี่ยนเมื่อไหร่ทุกชิ้นข้างใต้ต้องคิดใหม่
ตั้งค่าคงที่ที่ตัวตาราง ตัดการไหลลงไปทั้งตาราง วัดได้ 48–50 ms เหลือ 3 ms
🔴 ข้างในตารางห้ามมีชิ้นไหนอ่าน `--nav-w` เพราะจะได้ 0 เสมอ

## 4 · 🔴🔴 ทางที่ลองแล้วไม่ได้ผล ห้ามกลับไปใช้ (วัด 2 ต.ค. 2569)

| ลองอะไร | ผล |
|---|---|
| ตัวแปรค่อย ๆ เปลี่ยนแบบสืบทอด ตั้งที่กล่องนอกสุด | เฟรม 56–82 ms แย่กว่าเดิม |
| ตารางกว้างเท่าค่าที่มากกว่าระหว่างก่อนกับหลังกดตลอดช่วงเลื่อน เปลี่ยนจริงครั้งเดียวตอนจบ | ตารางวูบตอนจบ พี่กันเห็นว่า *"เด้ง"* |
| `content-visibility` กับข้อความในช่องที่อยู่นอกจอระหว่างเลื่อน | ไม่ช่วย แถมเพิ่มเฟรมช้าตอนกดและตอนจบอย่างละเฟรม |
| `content-visibility` กับแถวตาราง (`tr`) หรือช่อง (`td`) | ไม่มีผล เบราว์เซอร์ไม่ทำให้แถวและช่องตาราง |
| ถอดเส้นขอบ เงาเส้นแบ่งคอลัมน์ โหมดรวมเส้นขอบ (แปะทับชั่วคราว) | ไม่ช่วย และ 🔴 พี่กันสั่ง *"ห้ามถอดอะไรทั้งนั้น"* |
| ถอดชั้นวาดแยกของตาราง | ไม่ต่างในเงื่อนไข ข |
| ปิดการวัดตำแหน่งของแถบเลื่อนลอยระหว่างเลื่อน | ไม่ช่วย แค่ย้ายที่ที่เบราว์เซอร์คำนวณ |

## 5 · 🔴 วิธีวัดให้ถูก — ต้องดูเฟรมจริงในโครม

| กฎ | ทำไม |
|---|---|
| 🔴 **วัดในโครมที่พี่กันใช้** ห้ามย้ายไปวัดในเบราว์เซอร์ของแอปเอง | พี่กันด่า 2 ต.ค. 2569 *"ไปเทสในโครมจริงๆสิ"* |
| 🔴 **แท็บต้องมองเห็นอยู่** | แท็บที่ถูกบัง เบราว์เซอร์ไม่วาดเฟรม `requestAnimationFrame` ไม่วิ่ง `ResizeObserver` ไม่ยิง ตัวเลขหลอก |
| ดูช่วงห่างของเฟรม ไม่ใช่เวลาคำนวณอย่างเดียว | 16.7 ms = ลื่น · 33 50 66 = หลุดเฟรม · เวลาคำนวณตำแหน่งต่ำแต่เฟรมยังยาวได้ เพราะการวาดภาพกินเวลาด้วย |
| หาตัวถ่วงด้วยการแปะ CSS ชั่วคราวทีละอย่างในแท็บทดสอบ | ซ่อน tbody · ล็อกความกว้างตาราง · ลดแถวครึ่ง ตัวไหนลื่น = ตัวถ่วงอยู่ตรงนั้น |
| 🔴 รายงานผลทดลองต้องบอกว่า *แปะทับชั่วคราวในแท็บทดสอบ ไม่แตะโค้ด* | พี่กันเข้าใจว่าแคลร์จะถอดของจริง |
| แท็บที่ถูกบัง ถ่ายภาพได้ และทุกครั้งที่ถ่ายโครมวาดหนึ่งเฟรม | ใช้เทสการเลื่อนได้ (ไม่ใช่วัดความลื่น) |
