# หน้าจอมือถือ — กฎกลาง ใช้ได้ทุกโปรเจกต์

> 🗺️ เปิดคู่กับ — **`web-craft`** · **`form-input`** · **`button-feedback`** เพราะกฎหน้าจอใช้ร่วมกันหมด
> ตารางเต็มว่างานไหนต้องเปิดสกิลไหน อยู่ที่ `working-with-gun` ข้อ 0.0

> พี่กันสั่ง 1 ก.ย. 2569: *"ห้ามเปลี่ยนเดสก์ท็อปสักนิดเดียว แม้แต่ขยับ 1px ก็ห้าม
> เราเลยอยากทำ มันสร้างไฟล์แยกได้ไหม แบบแก้เฉพาะไฟล์นี้ เป็นของมือถือ"*

## ⚡ เจออาการไหน อ่านข้อไหน

ผู้ใช้อธิบายอาการด้วยสิ่งที่เห็น ไม่ใช่ด้วยสาเหตุ — ตารางนี้แปลจากสิ่งที่เห็นเป็นสาเหตุ

| ผู้ใช้บอกว่า | ให้ดูก่อนว่า | สาเหตุที่น่าจะเป็น |
|---|---|---|
| "หน้ามันเลื่อนไปมา" | **อะไรขยับ อะไรไม่ขยับ** ในภาพเดียวกัน | ดู 🏆 ด้านล่าง |
| ของที่ตรึงไว้ยังนิ่ง แต่เนื้อหาไถล | — | **พื้นที่เลื่อนเลื่อนแนวนอนได้** → ดีดกลับด้วย JS |
| ทุกอย่างขยับพร้อมกัน รวมแถบที่อยู่เบราว์เซอร์ | ขนาดตัวอักษรเปลี่ยนไหม | กรอบหน้าเว็บถูกลาก (ซูม หรือของล้น) |
| ตัวอักษร**ใหญ่ขึ้น** ในภาพที่มีอาการ | — | iPhone ซูมเอง → ช่องกรอกเล็กกว่า 16px |
| ตัวอักษร**เล็กลง** เนื้อหาไม่เต็มจอ | — | เบราว์เซอร์ย่อหน้าให้พอดี เพราะมีของกว้างเกิน |
| "แก้แล้วยังไม่หาย" ทั้งที่ตัวตรวจผ่าน | ผู้ใช้ได้โค้ดใหม่จริงหรือยัง | ใส่ป้ายเลขในชื่อเว็บให้ผู้ใช้ยืนยัน |

🚨 **อย่าเดาสาเหตุจากคำอธิบาย** — คำว่า "เลื่อนไปมา" ใช้ได้กับสาเหตุอย่างน้อย 4 แบบ
ที่แก้คนละวิธีกันหมด ขอภาพหรือคลิปแล้วดูว่าอะไรขยับ อะไรไม่ขยับ เสมอ

### ป้ายเลขในชื่อเว็บ — ท่าที่ประหยัดเวลาที่สุด

ก่อนไล่แก้รอบใหม่ ใส่เลขต่อท้ายชื่อเว็บ (`มูลค่ายาคืน 1` → `2` → `3`) ทุกครั้งที่ส่งของใหม่
ผู้ใช้เห็นเลขไหน = ได้โค้ดชุดนั้น ตัดข้อสงสัย "โค้ดถึงหรือยัง" ออกจากสมการทันที

🚨 **ใส่ฝั่งเดียวกับที่กำลังแก้เท่านั้น** (มือถือแก้ ก็ใส่ฝั่งมือถือ) และ**ลบทิ้งทันที**ที่ยืนยันแล้ว

## 🛑 ข้อแรกสุด — แยกไฟล์มือถือออกมาก่อนเสมอ

**ห้ามแก้หน้าจอมือถือด้วยการไปแก้ CSS กลางที่เดสก์ท็อปใช้ร่วมกัน**
ต่อให้แน่ใจแค่ไหนว่าไม่กระทบ — กฎที่ลืมครอบเงื่อนไขจะรั่วไปโดนเดสก์ท็อปแบบเงียบสนิท

### โครงที่ใช้

```
app/globals.css     ของเดิม ห้ามแตะเวลาทำงานมือถือ
app/mobile.css      🆕 ของมือถือทั้งหมด — ทุกบรรทัดขึ้นต้นด้วย .mrv-mobile
```

**ตั้งชื่อคลาสตามโปรเจกต์** (`mrv-mobile` · `drp-mobile` · `hcv-mobile`) ไม่ต้องใช้ชื่อกลาง
จะได้รู้ทันทีว่ากฎนี้ของเว็บไหนเวลาก๊อปข้ามโปรเจกต์

### 🚨 กฎ 3 ข้อของไฟล์นี้ ห้ามฝ่าฝืน

**① ทุกกฎต้องขึ้นต้นด้วยคลาสมือถือ ไม่มีข้อยกเว้น**

```css
/* ✅ */  .mrv-mobile [role="button"]:active { scale: 0.97; }
/* ❌ */  [role="button"]:active { scale: 0.97; }        /* รั่วไปโดนเดสก์ท็อปทันที */
```

**② ห้ามใช้ `@media (max-width: ...)` ตัดสินว่าเป็นมือถือ**

เว็บส่วนใหญ่มีปุ่ม "สลับดูแบบมือถือ" บนคอม — กดแล้วจอยังกว้าง 1366px อยู่
แต่หน้าจอเป็นแบบมือถือแล้ว · media query จะไม่ทำงานเลยในกรณีนั้น

**ต้องผูกกับธงตัวเดียวกับที่ JSX ใช้เลือกว่าจะวาดหน้าจอแบบไหน**

```js
// MedReturnApp.jsx (หรือคอมโพเนนต์แม่ของโปรเจกต์นั้น)
syncMobileClass = () => {
  if (typeof document === 'undefined') return;
  const st = this.state;
  const wide = (st.vw || 0) >= 1180 && !st.forceNarrow;   // ← ต้องตรงกับ vals/derive.js เป๊ะ
  document.body.classList.toggle('mrv-mobile', !wide);
};
```

เรียก 2 จุด — ตอนวัดจอ (`resize`) และตอน `componentDidUpdate` เมื่อ `vw` หรือ `forceNarrow` เปลี่ยน

🚨 **เงื่อนไขต้องตรงกับที่ JSX ใช้เป๊ะ ๆ** แก้ที่หนึ่งต้องแก้อีกที่เสมอ
ไม่งั้น CSS กับ JSX จะไม่ตรงกันแบบไม่มีอะไรเตือน

**③ ห้ามเขียนกฎที่กระทบขนาดหรือตำแหน่งของอะไรก็ตามบนเดสก์ท็อป**
ถ้าไม่แน่ใจว่ากฎไหนรั่ว ให้รันเครื่องมือตรวจ (ดูท้ายไฟล์)

## 📲 เปิดเป็นแอปบนหน้าจอโฮม — ทุกเว็บมือถือต้องทำ

**พี่กันสั่ง 1 ก.ย. 2569: "ข้อ 5 ตั้งเป็นสกิลหลักต้องทำ"**

เว็บที่เจ้าหน้าที่ใช้ทุกวันต้องเปิดจากหน้าจอโฮมได้เหมือนแอปจริง
ไม่ใช่ต้องเปิดเบราว์เซอร์แล้วหาที่อยู่เว็บทุกครั้ง

| ได้อะไร | ทำไมสำคัญ |
|---|---|
| ไอคอนวางบนหน้าจอโฮม | กดเข้าใช้งานได้ในกดเดียว ไม่ต้องพิมพ์ที่อยู่เว็บ |
| เปิดเต็มจอ ไม่มีแถบที่อยู่เว็บ | ได้พื้นที่จอคืนมาราว 90 จุด ซึ่งเยอะมากบนมือถือ |
| สลับแอปแล้วเห็นเป็นแอปแยกตัว | ไม่ปนกับแท็บเบราว์เซอร์อื่นสิบกว่าแท็บ |

### สิ่งที่ต้องมี

**① ไฟล์ประกาศตัวตนของแอป** — Next.js 15 ขึ้นไปใช้ `app/manifest.js`

```js
export default function manifest() {
  return {
    name: 'ชื่อเต็มของเว็บ',            // โชว์ตอนติดตั้ง
    short_name: 'ชื่อสั้น',              // โชว์ใต้ไอคอน ห้ามเกิน 12 ตัวอักษร
    description: '...',
    start_url: '/',
    display: 'standalone',              // 🚨 ตัวนี้แหละที่ทำให้เต็มจอ
    background_color: '#f6f7f4',        // สีตอนกำลังเปิด
    theme_color: '#2f7d5d',             // สีแถบสถานะบนสุด
    orientation: 'portrait',
    icons: [
      { src: '/icon-192.png', sizes: '192x192', type: 'image/png' },
      { src: '/icon-512.png', sizes: '512x512', type: 'image/png' },
      { src: '/icon-512.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' }
    ]
  };
}
```

**② ไอคอนเป็นไฟล์ PNG จริง** ขนาด 192 · 512 · 180 (ตัวหลังสำหรับ iPhone)

🚨 **iOS ไม่รับ SVG กับ data URI** ต้องเป็นไฟล์ PNG ใน `public/` เท่านั้น
   เว็บส่วนใหญ่มีไอคอนเป็น SVG อยู่แล้ว แปลงเป็น PNG ได้ด้วย puppeteer
   (เปิดหน้า HTML ที่ฝัง SVG แล้วถ่ายภาพตามขนาดที่ต้องการ)

**③ บอก iOS เพิ่ม** — iPhone ไม่อ่านไฟล์ประกาศตัวตนครบทุกช่อง ต้องบอกซ้ำใน `metadata`

```js
export const metadata = {
  appleWebApp: {
    capable: true,                      // เปิดเต็มจอบน iPhone
    statusBarStyle: 'default',          // ⚠️ ต้องถามเจ้าของงานก่อน ดูตารางด้านล่าง
    title: 'ชื่อสั้น'
  },
  icons: { icon: FAVICON, apple: '/icon-180.png' }
};
```

#### 🎨 `statusBarStyle` — เลือกเองไม่ได้ ต้องถามเจ้าของงาน

> พี่กันสั่งไว้ตอนเลือกให้เว็บ ME-DRP เป็นแบบเขียวเต็ม (9 ก.ย. 2569)
> *"**อันนี้เฉพาะเว็บนี้นะ เว็บอื่นอาจจะไม่ บอกไว้ก่อน**"*

| ค่า | หน้าตา | ต้องทำอะไรเพิ่ม |
|---|---|---|
| `'default'` | พื้นตามสีเว็บ ตัวหนังสือดำ · **มีแถบคั่นก่อนถึงหัวเว็บ** | ไม่ต้อง — ปลอดภัยที่สุด |
| `'black'` | พื้นดำ ตัวหนังสือขาว | ไม่ต้อง |
| `'black-translucent'` | **โปร่งใส ตัวขาว · หัวเว็บลากสีเต็มถึงขอบบน** | **ต้องทำครบ 3 อย่าง ดูด้านล่าง** |

🚨🔴 **นี่คือการตัดสินใจเรื่องหน้าตา ไม่ใช่กฎเทคนิค — ห้ามเลือกเอง ห้ามยกข้ามเว็บ**
เว็บหนึ่งเอาแบบเขียวเต็ม ไม่ได้แปลว่าอีกเว็บเอาด้วย · **ทำมอคอัปเทียบให้เจ้าของงานเลือก**
(ตัวอย่างมอคอัปเทียบ 3 แบบ: `ME-DRP-fresh/docs/mockups/statusbar-2026-09-09.svg`)
🚨 **มอคอัปที่ทำต่อจากนี้ให้เขียนเป็น `.html` ไม่ใช่ `.svg`** — ดูสกิล `working-with-gun` ข้อ 4.4.5

## 📴 เน็ตหลุดแล้วยังเปิดเว็บได้ (9 ก.ย. 2569 · ข้อ 23)

**ไฟล์ประกาศตัวตนแอปอย่างเดียวไม่ได้ทำให้เว็บใช้ตอนไม่มีเน็ตได้**
เพิ่มลงหน้าจอโฮมแล้วกดเปิดตอนเน็ตหลุด = ยังได้จอขาว "ไม่มีอินเทอร์เน็ต" เหมือนเดิม
เพราะไฟล์เว็บทั้งหมดยังอยู่ที่เซิร์ฟเวอร์ · ต้องมีตัวเก็บสำเนา (`public/sw.js`) แยกอีกชุด

### 🚨🔴🔴 เว็บที่มีข้อมูลคนไข้ ห้ามแคชคำตอบจากหลังบ้านเด็ดขาด

```js
// 🚨 บรรทัดนี้สำคัญที่สุดในไฟล์ — ข้อมูลผู้ป่วยทั้งหมดวิ่งผ่านเส้นนี้
if (url.pathname.startsWith("/api/")) return;   // ปล่อยผ่าน ไม่แตะแคช
if (url.pathname === "/login") return;          // ให้เซิร์ฟเวอร์ตัดสินบัตรผ่านทุกครั้ง
if (req.method !== "GET") return;               // บันทึก/แก้/ลบ ต้องถึงเซิร์ฟเวอร์จริง
```

🔑 **แคชแค่เปลือกเว็บก็แก้ปัญหาจอขาวได้ครบแล้ว** โดยไม่ต้องเก็บข้อมูลคนไข้เพิ่มสักชิ้น
— ประเด็น PDPA จึงหายไปทั้งก้อน **ไม่ต้องแลกอะไรเลย**

### กลยุทธ์แคช 3 แบบ ใช้คนละที่

| ของ | วิธี | เพราะ |
|---|---|---|
| ไฟล์ที่มีรหัสในชื่อ (`/_next/static/`) | **แคชก่อน** | รุ่นใหม่ = ชื่อไฟล์ใหม่ ไม่มีทางได้ของเก่าผิดรุ่น |
| หน้าเว็บ | **เอาของสดก่อน** เน็ตหลุดค่อยใช้สำเนา | เว็บแก้บ่อย และต้องผ่านด่านรหัสผ่านทุกครั้ง |
| ไอคอน / ไฟล์ประกาศตัวตน | ใช้ของเก่าไปก่อน แล้วแอบโหลดใหม่ทับ | เปลี่ยนน้อย แต่ควรตามให้ทัน |

🚨 **ตอนติดตั้งใช้ `Promise.allSettled` ไม่ใช่ `cache.addAll`**
`addAll` ล้มทั้งชุดถ้าไฟล์เดียวโหลดไม่ได้ แล้วตัวเก็บสำเนาจะติดตั้งไม่สำเร็จเลย

🚨 **ต้องมีเลขรุ่นในชื่อแคช และล้างรุ่นเก่าตอนเปิดใช้งาน** ไม่งั้นแคชเก่าค้างถาวร

🚨 **ตอนรันในเครื่อง (localhost) ห้ามลงทะเบียน** และให้ถอนตัวเก่าทิ้งด้วย
ไม่งั้นแก้โค้ดแล้วเบราว์เซอร์หยิบของเก่ามาแสดง นั่งงงว่าทำไมแก้แล้วไม่เปลี่ยน

🚨 **ต้องเขียนวิธีถอนไว้ในหัวไฟล์** ตัวนี้ฝังในเครื่องผู้ใช้ ถอนยากกว่าโค้ดปกติ

## 📲 แถบชวนติดตั้ง (9 ก.ย. 2569 · ข้อ 25)

```js
window.addEventListener("beforeinstallprompt", (e) => {
  e.preventDefault();   // 🚨 ไม่ห้าม เบราว์เซอร์จะเด้งแถบเล็ก ๆ ของตัวเองที่ไม่มีใครเห็น
  เก็บสัญญาณไว้(e);      // 🚨 สัญญาณใช้ได้ครั้งเดียว ใช้แล้วต้องทิ้ง
});
```

| เงื่อนไข | ทำไม |
|---|---|
| เปิดจากไอคอนอยู่แล้ว (`display-mode: standalone`) ไม่ต้องชวน | ติดตั้งไปแล้ว |
| กด "ไว้ก่อน" = เงียบ 30 วัน | เว็บที่เปิดวันละหลายรอบ ถ้าเด้งทุกครั้งคนจะกดปิดโดยไม่อ่าน |
| **ไอโฟนไม่มีแถบนี้** | ซาฟารีไม่มีสัญญาณนี้ และไม่ยอมให้เว็บเรียกหน้าต่างติดตั้งเอง |

🚨 **ไอโฟนทำได้อย่างเดียวคือป้ายสอนพร้อมลูกศรชี้ปุ่มแชร์** — ถ้าเจ้าของเว็บไม่เอา ก็ไม่ต้องมี

### 🚨🔴🔴 เว็บที่มีด่านรหัสผ่าน ต้องเปิดทางให้ไฟล์สาธารณะโหลดได้เอง

**เจอจริง 9 ก.ย. 2569 — ทำไอคอนครบทุกไฟล์แล้วแต่ติดตั้งไม่ได้**
ด่านรหัสผ่านยกเว้นแค่ `icon.svg` แต่ไฟล์ประกาศตัวตนแอปชี้ไปหา `/icon-192.png`
ซึ่ง**เบราว์เซอร์โหลดเองนอกรอบโดยไม่แนบบัตรผ่าน** → โดนเด้งไปหน้าเข้าสู่ระบบ

```ts
// ต้องยกเว้นให้ครบทุกไฟล์ที่เบราว์เซอร์โหลดเอง
```

### 🚨 กับดักที่ต้องรู้

- 🔴 **ต้องเป็น https เท่านั้น** — เปิดผ่าน `http://192.168.x.x` จะไม่มีเมนู "เพิ่มลงหน้าจอโฮม"
  ทดสอบบนเว็บจริงหลัง deploy เท่านั้น เครื่องทดสอบในเครื่องดูไม่ได้
- 🔴 **`display: 'standalone'` ทำให้ไม่มีปุ่มย้อนกลับของเบราว์เซอร์**
  เว็บต้องมีทางกลับของตัวเองทุกหน้า ไม่งั้นผู้ใช้ติดอยู่ในหน้านั้นถาวร
- 🔴 **ไอคอน maskable ต้องเผื่อขอบ** Android ตัดไอคอนเป็นวงกลม/สี่เหลี่ยมมนตามธีมเครื่อง
  ของสำคัญต้องอยู่ในวงกลมกลางภาพ 80% ไม่งั้นโดนตัดขอบ
- 🔴 **`short_name` เกิน 12 ตัวอักษรจะโดนตัดด้วยจุดไข่ปลา** ใต้ไอคอนบนหน้าจอโฮม
- ⚠️ **ไม่ได้แปลว่าใช้ตอนไม่มีเน็ตได้** อันนั้นต้องทำ service worker เพิ่มอีกชุด
  เว็บที่ต้องต่อฐานข้อมูลตลอดเวลาไม่ได้ประโยชน์จากตรงนั้นมากนัก

### วิธีตรวจ

1. เปิดเว็บจริง (https) บนมือถือ → กดปุ่มแชร์ → ต้องเห็น "เพิ่มลงหน้าจอโฮม"
2. เพิ่มแล้วดูไอคอนบนหน้าจอโฮม — ต้องเป็นไอคอนของเว็บ ไม่ใช่ภาพหน้าจอย่อ
3. กดไอคอน → ต้องเปิดเต็มจอ ไม่มีแถบที่อยู่เว็บ
4. ตรวจไฟล์ประกาศตัวตนด้วย `curl https://<โดเมน>/manifest.webmanifest`

## สิ่งที่ทำให้เว็บ "รู้สึกเป็นแอป" — เรียงตามคุ้มที่สุด

### 🟢 ทำก่อน — CSS ไฟล์เดียว ได้ผลเยอะ

| ทำอะไร | ได้อะไร |
|---|---|
| **ปุ่มยุบตอนกด** (`scale: 0.97` ที่ `:active`) | แตะปุ่มปุ๊บรู้ทันทีว่าโดน |
| **`touch-action: manipulation` บนปุ่ม** | ปิดซูมตอนแตะสองครั้ง ปุ่มตอบไวขึ้น |
| **`user-select: none` บนปุ่ม** | แตะปุ่มแล้วตัวหนังสือไม่ถูกลากไฮไลต์ |
| **`overscroll-behavior: contain`** บนกล่องที่เลื่อนได้ | เลื่อนสุดในกล่องแล้วหน้าข้างหลังไม่ไหลตาม |
| **`dvh` แทน `100vh`** | ของไม่ล้นจอตอนแถบเบราว์เซอร์ยืดหด |
| **`env(safe-area-inset-*)`** | เนื้อหาไม่โดนติ่งจอกับแถบท่าทางล่างบัง · ⚠️ **มีค่าจริงเมื่อตั้ง `viewportFit: 'cover'` เท่านั้น** |
| `viewportFit: 'cover'` | ให้เว็บไหลถึงขอบจอจริง · 🚨 **ไม่ใช่ของที่ต้องมีทุกเว็บ — ถามเจ้าของงานก่อน** ดูหัวข้อ `statusBarStyle` |
| **`:focus-visible` แทน `:focus`** | ปุ่มไม่ค้างขอบเรืองหลังแตะ แต่คีย์บอร์ดยังใช้ได้ |

### 🚨 กับดักที่เจอจริง

**ปิดไฮไลต์ตอนแตะแล้วต้องใส่อะไรแทนเสมอ**

```css
* { -webkit-tap-highlight-color: transparent; }   /* ปิดแล้ว... */
```

ถ้าสีที่ทำไว้ทั้งเว็บเป็น `:hover` ล้วน — **จอสัมผัสไม่มี hover**
ผลคือแตะปุ่มแล้วเงียบสนิท ไม่รู้ว่านิ้วโดนหรือยัง **แย่กว่าไม่ปิดไฮไลต์เลย**

**ใช้ `scale` ไม่ใช่ `transform`**
ปุ่มหลายตัวมี `transform` อยู่แล้ว (เช่นปุ่ม ✕ ที่ใช้ `translateY` จัดกึ่งกลาง)
เขียนทับด้วย `transform` แล้วปุ่มจะกระโดดออกจากตำแหน่งตอนกด

**ตัวเลือกต้องตรงกับปุ่มจริงในโปรเจกต์นั้น**
เว็บที่ปุ่มเป็น `<div role="button">` (ไม่ใช่ `<button>` จริง) ต้องเขียน `[role="button"]`
ก๊อป CSS จากเว็บที่ใช้ `<button>` มาตรง ๆ จะไม่มีผลกับปุ่มสักตัวเดียว

**`user-select: none` ห้ามใส่ทั้งหน้า**
ใส่เฉพาะปุ่มกับป้าย — ไม่งั้นคัดลอกชื่อยา เลข HN เลขเอกสาร ไม่ได้ ซึ่งเป็นการใช้งานจริง

## 🚨 พื้นที่กดทับกัน — อันตรายที่สุดบนจอสัมผัส

คลาสที่ขยายพื้นที่กด (เช่น `.tap::before { inset: -11px }`) **ห้ามใส่กับปุ่มคู่ที่วางติดกัน**

ปุ่มที่ห่างกันน้อยกว่า 2 เท่าของระยะที่ขยาย จะมีพื้นที่กดซ้อนกัน
→ เล็งกดปุ่มหนึ่ง แต่โดนอีกปุ่ม **โดยไม่มีอะไรเตือน**

**ทางแก้ที่ถูก** — ขยายตัวปุ่มเองให้ถึง 44px แล้วถอดคลาสขยายพื้นที่กดออก

```jsx
/* ❌ */ <div className="tap" style={s('padding:5px 10px')}>ใช้ต่อ</div>
/* ✅ */ <div style={s('min-height:44px;min-width:56px;display:flex;align-items:center;justify-content:center;padding:5px 12px')}>ใช้ต่อ</div>
```

🚨 **ห้ามแค่ถอดคลาสเฉย ๆ** ปุ่มจะเหลือเล็กกว่าเกณฑ์นิ้ว กดยากกว่าเดิม

### 🚨 ช่องกรอกใช้ท่าเดียวกับปุ่มไม่ได้ (ข้อ 20 · 9 ก.ย. 2569)

```css
/* ปุ่ม — จัดกึ่งกลางด้วย flex ได้ */
.hit { min-width: 44px; min-height: 44px; display: flex; align-items: center; justify-content: center; }

/* ช่องกรอก — ห้ามใส่ display:flex เด็ดขาด */
input.hit, textarea.hit, select.hit { min-height: 44px; display: revert; }
```

🚨 **`<input>` วาดข้อความข้างในด้วยกลไกของเบราว์เซอร์เอง ไม่ใช่ระบบวางกล่องปกติ**
เปลี่ยน `display` เป็น `flex` แล้ว **ข้อความในช่องเพี้ยน** — บางเบราว์เซอร์ตัวอักษรลอยไปชิดบน
บางตัวเคอร์เซอร์ไปอยู่คนละที่กับตัวอักษร · และวรรณยุกต์ไทยโดนตัดซ้ำอีกชั้น

🔑 **ช่องกรอกให้ดันความสูงอย่างเดียวก็พอ** (`min-height` + `padding`)
ข้อความจัดกึ่งกลางให้เองอยู่แล้วโดยไม่ต้องสั่ง

**เคสที่ต้องรีบแก้ที่สุด** คือปุ่มคู่ที่ผลลัพธ์ตรงข้ามกัน — ใช้ต่อ ↔ ทำลาย · อนุมัติ ↔ ปฏิเสธ · แก้ ↔ ลบ
กดผิดแล้วข้อมูลเปลี่ยนความหมายทันที

## เครื่องมือพิสูจน์ว่าเดสก์ท็อปไม่ขยับ

**รันทุกครั้งที่แตะไฟล์มือถือ** — `scripts/desktop-untouched-check.mjs`

วิธีที่ใช้: วัดพิกัด ขนาด ระยะขอบ ฟอนต์ ของทุกปุ่มบนหน้าเดสก์ท็อป **3 รอบ**

## 🖼 มอคอัปหน้าจอมือถือ — กรอบต้องกว้างเท่าจอจริง

🔑 **กฎมอคอัปฉบับเต็มอยู่สกิล `working-with-gun` ข้อ 3.5 ๖** (ทำก่อนเขียนโค้ด ·
มีของครบเหมือนหน้าจริง · กรอบเท่าขนาดจริง · ป้ายตัวเลขต้องคำนวณเอง)
ตรงนี้เก็บเฉพาะค่าที่ใช้กับจอมือถือ

**ความกว้างที่ใช้วาดกรอบ**

| ใช้ตอนไหน | กว้าง |
|---|--:|
| กรอบมอคอัปมาตรฐาน (ตรงกับที่เทสจริง) | **424px** |
| iPhone รุ่นเล็กสุดที่ยังต้องรองรับ (SE) | **375px** |
| จุดตัดที่โค้ดใช้แยกมือถือ/เดสก์ท็อป | `max-width: 640px` |

🚨 **วางเรียงลงมาแนวตั้ง อย่าวางเรียงข้างกันแล้วย่อกรอบ**
บีบเมื่อไหร่ปุ่มจะตกบรรทัดผิดจากของจริงทันที เพราะพื้นที่ในกล่องเหลือน้อยกว่าที่คิดเสมอ

**คำนวณพื้นที่ที่เหลือจริงก่อนวาด** — ตัวอย่างจากหน้ารายงาน ME-DRP

```
จอ 424
− ขอบหน้า 18 × 2          = 388   ความกว้างกล่องขาว
− เส้นขอบกล่อง 1 × 2
− ขอบในกล่อง 14 × 2       = 356   ← พื้นที่ที่ปุ่มใช้ได้จริง
```

**356px ไม่ใช่ 424px** — ต่างกัน 68px ซึ่งพอทำให้ปุ่มตกบรรทัดได้สบาย ๆ
วัดผลรวมความกว้างของทุกชิ้นในแถว (รวมช่องไฟ) เทียบกับเลขนี้ก่อนเสมอ

```js
// วางในคอนโซลตอนเปิดมอคอัป — บอกว่าเกินไปกี่พิกเซล
const แถบ = document.querySelector('.bar');
const พื้นที่ = แถบ.clientWidth - 28;                    // หักขอบใน 14 สองข้าง
const ชิ้น = [...แถบ.querySelector('.line').children];
const รวม = ชิ้น.reduce((a, el) => a + el.getBoundingClientRect().width, 0)
          + 8 * (ชิ้น.length - 1);                      // ช่องไฟระหว่างชิ้น
console.log({ พื้นที่, รวม, เกิน: รวม - พื้นที่ });
```

## 🔴 หน้าเว็บเลื่อนซ้ายขวาได้ = บั๊กเสมอ

พี่กันถ่ายวิดีโอมาให้ดู 1 ก.ย. 2569: *"เราไม่อยากให้มันเลื่อนไปมาแบบนี้"*
หน้าไถลไปทางขวา 74px ตัวหนังสือฝั่งขวาหายนอกจอ — ป้ายเตือน ปุ่มลบ ชิปตัวสุดท้าย

### กับดักที่ทำให้เกิด — flex คอลัมน์ที่จัดกึ่งกลาง

```jsx
/* พ่อ */ <div style="display:flex;flex-direction:column;align-items:center">
/* ลูก */   <div style="min-width:0">
/*      */     <span style="white-space:nowrap">ข้อความยาว 539px</span>
```

`align-items: center` ทำให้ลูก **ไม่ถูกยืดเต็มความกว้าง** แต่กว้างเท่าเนื้อหาแทน
`min-width: 0` ที่ตัวลูกจึงไม่ช่วยอะไรเลย เพราะไม่มีอะไรมาบีบตั้งแต่แรก

**ทางแก้: `max-width: 100%` ที่ลูก** — บนมือถือให้ขึ้นบรรทัดใหม่ ไม่ตัดด้วยจุดไข่ปลา
(ชื่อหน่วยงานที่เหลือครึ่งเดียวตลอดแย่กว่าสองบรรทัด)

### ประกาศเจตนาที่พื้นที่เลื่อน

```css
.mrv-mobile [role="main"] { overflow-x: clip; }   /* 🚨 clip ไม่ใช่ hidden — ดูหัวข้อท้ายไฟล์ */
```

🚨 **ไม่ใช่ที่ซ่อนขยะ** — ของที่ล้นจริงต้องแก้ที่ตัวมันเสมอ
กฎนี้กันเศษ 1-2px ที่มาจากพื้นที่กดขยายของปุ่มชิดขอบจอ (`::before`) ซึ่งมองไม่เห็นอยู่แล้ว

🚨 **ใส่ที่พื้นที่เลื่อนจริง ไม่ใช่ที่ `body`** — เว็บที่ตรึงความสูงเท่าจอ ตัวที่เลื่อนคือ div ตัวใน

### เครื่องมือ — `scripts/overflow-check.mjs`

วัดจากขนาดจริงของทุกกล่อง ไม่ได้ดูแค่ว่าแถบเลื่อนโผล่ไหม

```
ความกว้างเอกสาร 390 · จอ 390          ← เท่ากัน = ผ่าน
ของที่ยื่นออกนอกจอ
  div "฿ มูลค่ายาคืน v0.15.1.0 · "  ซ้าย -74 ขวา 464 (กว้าง 539)   ← ต้นเหตุ
```

🚨 **ต้องรายงานเฉพาะตัวที่พ่อไม่ได้ล้นด้วย** ไม่งั้นได้รายชื่อลูกหลานที่ล้นตามพ่อเป็นร้อยบรรทัด
🚨 **ต้องตรวจทั้ง `document.scrollWidth` และกล่องที่ `scrollWidth > clientWidth`**
เว็บที่ตรึงความสูง `document` จะไม่โตเลย แต่กล่องข้างในเลื่อนได้ — ดูอย่างเดียวจะไม่เจอ

## ท่ามาตรฐานที่ทำให้รู้สึกเป็นแอป — 2 อย่างที่คุ้มที่สุด

### ① ดึงลงเพื่อโหลดใหม่

```js
PULL_MAX = 92;    // ลากได้ไกลสุด
PULL_FIRE = 62;   // ถึงเท่านี้แล้วปล่อย = สั่งโหลด
```

- 🚨 **ต้องอยู่บนสุดของพื้นที่เลื่อนเท่านั้น** (`scrollTop === 0`) ไม่งั้นเลื่อนดูตารางกลางหน้าแล้วโดนดึงมั่ว
- 🚨 **หารระยะที่นิ้วลากครึ่งหนึ่ง** ให้รู้สึกฝืดเหมือนยางยืด · ลากเท่าไหร่ขยับเท่านั้นจะลื่นเกินจนเผลอสั่งบ่อย
- 🚨 **`touchmove` ต้องผูกแบบ `passive: false`** เพื่อ `preventDefault` ได้ ไม่งั้นการเด้งของเบราว์เซอร์สู้กับของเรา ภาพกระตุก
- 🚨 **`overscroll-behavior-y: contain`** ปิดการรีเฟรชทั้งหน้าของ Chrome แอนดรอยด์ — ไม่งั้นดึงทีเดียวได้สองอย่าง และร่างที่กรอกค้างเสี่ยงหาย
- 🚨 **ตั้งเวลาขั้นต่ำ ~420ms** ไม่งั้นเน็ตเร็ว ๆ ตัวหมุนแวบเดียวจนดูเหมือนไม่ได้ทำอะไร
- 🚨 **ระหว่างลากห้ามมี transition** เขียน `transition:none` ทับใน inline style · ปล่อยนิ้วแล้วค่อยให้ CSS ไล่กลับ
- **ข้อความต้องเปลี่ยนตามระยะ** — "ดึงลงเพื่อโหลดใหม่" → "ปล่อยเพื่อโหลดใหม่" → "กำลังโหลดข้อมูลใหม่"
  ไม่งั้นไม่มีทางรู้ว่าลากพอหรือยัง

### ② เปลี่ยนหน้าไม่วาบ (View Transitions)

```js
if (typeof document.startViewTransition === 'function' && เป็นมือถือ) {
  document.startViewTransition(() => setState({ screen: name }));
} else { setState({ screen: name }); }
```

- 🚨 **ห้ามเขียนแอนิเมชันเอง** — ต้องประวิงการถอด DOM ไว้ ซึ่งพังทันทีที่ state เปลี่ยนระหว่างทาง
- 🚨 **กดแท็บเดิมซ้ำต้องไม่ไล่จาง** เช็ค `screen === name` แล้ว return
- 🚨 **ห้ามใช้กับหน้าต่างซ้อน (ป๊อป)** — ภาพนิ่งที่เบราว์เซอร์ถ่ายไว้จะกินคลิกไปด้วย
- CSS ของมันเป็น pseudo ระดับเอกสาร ซ้อนใต้คลาสไม่ได้ → ล้อมด้วย `:root:has(body.mrv-mobile)`

### สิ่งที่ลองแล้ว "ไม่พอ" (แต่ยังควรมีไว้)

| ทำอะไร | ทำไมไม่พอ |
|---|---|
| แก้ของที่ล้นจอทีละตัว | มือถือแต่ละรุ่นวาดฟอนต์กว้างไม่เท่ากัน ไม่มีวันจบ |
| `overflow-x: hidden / clip` | ได้ผลบนคอม บนมือถือจริงยังลากได้ |
| `touch-action: pan-y` | เหมือนกัน |
| `max-width: 100vw` ทุกชั้น | เหมือนกัน |
| `position: fixed` ทั้งแอป | fixed ยึดกับ **กรอบผัง** ไม่ใช่ขอบจอ จึงถูกลากไปด้วย |
| วัดขอบจอแล้วล็อกความกว้าง | ล็อกได้จริง แต่ยังลากได้ |
| ห้ามซูม (`user-scalable=no` + ดัก gesture) | ปิดการซูมได้จริง แต่คนละเรื่องกับการลาก · **ยังต้องทำอยู่ดี** (ดูหัวข้อ "ห้ามซูมทุกเว็บ") แค่ไม่ใช่ตัวแก้เรื่องหน้าไถล |

### ✅ สิ่งที่แก้ได้จริง — ดีดตำแหน่งเลื่อนกลับ 0

เลิกห้าม แล้วปล่อยให้ดันไป **แต่ดีดกลับเป็น 0 ทันทีทุกครั้ง**

```js
_pinLeft = () => {
  if (!document.body.classList.contains('mrv-mobile')) return;   // 🚨 คอมต้องไม่โดน
  const sc = this.scrollRef.current;
  if (sc && sc.scrollLeft !== 0) sc.scrollLeft = 0;
  const de = document.documentElement;
  if (de && de.scrollLeft !== 0) de.scrollLeft = 0;
  if (document.body.scrollLeft !== 0) document.body.scrollLeft = 0;
  if (window.scrollX !== 0) window.scrollTo(0, window.scrollY);
};

document.addEventListener('scroll', this._pinLeft, { passive: true, capture: true });
window.addEventListener('scroll',   this._pinLeft, { passive: true });
window.addEventListener('touchmove', this._pinLeft, { passive: true });
window.addEventListener('touchend',  this._pinLeft, { passive: true });
```

- 🚨 **ต้องดัก `touchmove` ด้วย** — บางเบราว์เซอร์ไม่ยิง `scroll` ระหว่างนิ้วยังลากอยู่ ดักแค่ scroll จะเห็นภาพไถลก่อนแล้วค่อยดีดกลับ
- 🚨 **ต้อง `capture: true` ที่ document** — จับกล่องข้างในที่เลื่อนเองได้ทุกตัว ไม่ใช่แค่ตัวที่รู้จัก
- 🚨 **`passive: true` ได้และควรใช้** — ไม่ได้ห้ามเหตุการณ์ แค่ตั้งค่ากลับ จึงไม่ถ่วงการเลื่อนขึ้นลงเลย
- 🚨 **ต้องเช็คว่าเป็นมือถือก่อนเสมอ** — ตารางกว้างฝั่งคอมต้องเลื่อนดูข้าง ๆ ได้จริง

```
โหลดหน้า → วาดจอรอบแรก (ยังไม่มีคลาส) → ผู้ใช้แตะจอได้แล้ว → คลาสเพิ่งถูกใส่
                                          └── ช่วงนี้ไม่มีการป้องกันเลย
```

🚨 **การป้องกันที่ต้องมีตั้งแต่วินาทีแรก ให้ผูกกับความกว้างจอโดยตรง ไม่ใช่ผูกกับคลาส**

## 🔴🔴🔴 ห้ามซูมทุกเว็บ — พี่กันเคาะเอง (ข้อ 19 · 9 ก.ย. 2569)

> *"เราว่า **ห้ามซูมมมม ทั้งหมด จบ ไม่สนเรื่องคนสายตายาว**
>  ยกเว้นพี่เภสัชบอกให้ขยายฟอนต์ 5555"*
>
> ตอนสั่งครั้งแรก 1 ก.ย. 2569: *"งั้น ห้ามซูม เหมือนจุดที่ตรึงไว้ของปุ่มกดส่งยา
>  **เพราะแอปทั่วไป มันซูมไม่ได้ นี่นา**"* · *"ห้ามซูม ลองดูแบบนี้ด้วย ห้ามขยายด้วย"*

### ⚠️ กฎข้อนี้เคยเขียนกลับด้าน — แก้แล้ว 9 ก.ย. 2569

ไฟล์นี้เคยเขียนไว้ **3 ที่** ว่า `user-scalable=no` / `maximum-scale=1` เป็นสิ่งที่ **"ห้ามทำเด็ดขาด"**
ด้วยเหตุผลว่าผิด WCAG 1.4.4 (คนสายตายาวซูมอ่านไม่ได้)

**แต่พี่กันสั่งให้ทำมาตั้งแต่ 1 ก.ย. 2569 และยืนยันซ้ำวันที่ 9** — เหตุผลค้างอยู่ในคอมเมนต์ไฟล์เว็บยาคืน
ไฟล์เดียวมาตลอด ไม่เคยขึ้นสกิล **สกิลจึงมีสองคำตอบขัดกันเองอยู่ 8 วัน**

🚨 **แคลร์เคยทักท้วงเรื่องการเข้าถึงไปแล้ว พี่กันฟังแล้วยืนยัน** — จบ ไม่ต้องทักซ้ำอีก
🔑 **ผู้ใช้อ่านไม่เห็น = ไปขยายฟอนต์ในเว็บให้ ไม่ใช่ปล่อยให้ซูมเอา** (ขนาดฟอนต์เจ้าของงานเกลาเอง ไม่มีค่ากลาง)

### เหตุผลที่ห้ามซูม

| เหตุผล | รายละเอียด |
|---|---|
| **แอปจริงซูมไม่ได้** | เว็บที่ซูมได้รู้สึกเป็นเว็บทันที · เป้าหมายคือให้รู้สึกเป็นแอป |
| **ซูมแล้วไม่ซูมกลับ** | iOS ค้างในสภาพซูม ลากไปมาได้ทั้งหน้ารวมแถบที่อยู่ · ผู้ใช้บอกว่า "เว็บมันเลื่อนไปมา" |
| **ไม่ใช่เว็บสาธารณะ** | เว็บของหน่วยงาน ใช้บนเครื่องเจ้าหน้าที่เอง |

### วิธีทำ — ต้องครบ 4 ชั้น ชั้นเดียวไม่พอ

**ชั้นที่ 1 · viewport**

```js
export const viewport = { maximumScale: 1, userScalable: false };
```

⚠️ **iOS 10 ขึ้นไปไม่สนใจ `user-scalable` ในหลายกรณี** บรรทัดนี้อย่างเดียวจึงไม่พอ

**ชั้นที่ 2 · `touch-action` ครอบทุก element**

```css
@media (max-width: <จุดสลับ − 1>) {
  html, body, body * { touch-action: pan-y !important; }
}
```

🚨 **ต้องครอบ `body *` ด้วย** — `touch-action` **ไม่สืบทอดลงไปยังลูก**
เบราว์เซอร์ดูค่าของ element ที่นิ้วแตะโดยตรง · ใส่ที่ `body` อย่างเดียว แล้วนิ้วไปแตะการ์ดข้างใน = ซูมได้ตามปกติ

🚨 **ต้องใช้ `@media` ไม่ใช่คลาสที่ JS ใส่** — คลาสถูกใส่หลังหน้าโหลดเสร็จ
**ช่วงก่อนหน้านั้นซูมได้ ลากได้ แล้วค้างไปทั้งรอบ** (พี่กันเจอตอนรีเฟรชเข้ามาใหม่)

⚠️ `pan-y` = เลื่อนขึ้นลงได้อย่างเดียว · ไม่บีบซูม ไม่ลากข้าง ไม่แตะสองครั้งขยาย
**การแตะปุ่มปกติไม่ถูกกระทบ** (การแตะไม่ใช่การ pan)

🚨 **กฎนี้กว้างมาก — เว็บที่มีแผนที่ · รูปที่ต้องซูมดู · ตารางที่เลื่อนข้างได้ จะพังทันที**
ต้องตั้ง `touch-action: pan-x pan-y` ที่กรอบพวกนั้นเองเพื่อยกเว้น

**ชั้นที่ 3 · ดักท่าซูมของ Safari ด้วย JS**

```js
['gesturestart', 'gesturechange', 'gestureend'].forEach((ev) =>
  document.addEventListener(ev, (e) => e.preventDefault(), { passive: false })
);
```

🚨 **ต้องผูกใน constructor ไม่ใช่ `componentDidMount`** — บนมือถือ mount ช้ากว่าหลายวินาที
ช่วงนั้นผู้ใช้แตะจอได้แล้วแต่ยังไม่มีอะไรกัน

**ชั้นที่ 4 · ห้ามเบราว์เซอร์ขยายตัวอักษรเอง**

```css
html { -webkit-text-size-adjust: 100%; text-size-adjust: 100%; }
```

### 🚨 ห้ามซูม ≠ เลิกทำ 16px — คนละเรื่องกันสิ้นเชิง

| เรื่อง | คืออะไร | ยังต้องทำไหม |
|---|---|---|
| **ช่องกรอกไม่ต่ำกว่า 16px** | **iOS ซูมเอง**ตอนแตะช่องเล็กกว่า 16px แล้วไม่ซูมกลับ | ✅ **ต้องทำเสมอ ทุกเว็บ** |
| ห้ามซูม | **คนซูมเอง**ด้วยสองนิ้ว | ✅ ตามกฎนี้ |

🔴 **การซูมอัตโนมัติของ iOS เป็นบั๊กประสบการณ์ ไม่ใช่ความต้องการของผู้ใช้**
ต่อให้ห้ามซูมครบ 4 ชั้นแล้ว ถ้าช่องกรอกยังเล็กกว่า 16px หน้าก็ยังกระตุกอยู่ดี

## 🔴 `touch-action` ไม่สืบทอดลงไปยังลูก

**เบราว์เซอร์ดูค่าของสิ่งที่นิ้วแตะโดยตรง** ไม่ได้ไล่ขึ้นไปดูของแม่
ใส่ที่ตัวหน้าเว็บอย่างเดียว **แล้วนิ้วไปแตะโดนกล่องข้างในซึ่งไม่มีค่านั้น = ไถลได้ตามปกติ**

🚨 **ต้องใส่ให้ครอบคลุมลูกด้วย** เช่นตั้งกฎที่ครอบทุกอย่างในพื้นที่นั้น

### 🚨🔴 แต่กฎที่ครอบทุกอย่าง จะพังของที่ต้องลากดูทันที (ข้อ 18 · 9 ก.ย. 2569)

`pan-y` = **เลื่อนขึ้นลงได้อย่างเดียว** — ห้ามบีบซูม ห้ามแตะสองครั้งขยาย **และห้ามลากข้างด้วย**
พอครอบทุกชิ้นในหน้า ของพวกนี้จะเลื่อนดูไม่ได้เลย

| ของที่พัง | อาการ |
|---|---|
| แถวชิป / แถบแท็บที่ยาวเกินจอ | ปุ่มที่โผล่พ้นขอบจอ **ลากมาหาไม่ได้ตลอดกาล** |
| ตารางที่กว้างเกินจอ | เห็นแค่คอลัมน์ซ้าย ที่เหลือดูไม่ได้ |
| แผนที่ · รูปที่ต้องซูมดู | ใช้ไม่ได้เลย |

**ทางแก้ — ยกเว้นให้กรอบพวกนั้นเอง**

```css
/* เว็บที่เขียนสไตล์ฝังในแท็ก ไม่มีคลาสให้เกาะ — จับจากตัวสไตล์เองเลย */
[style*="overflow-x"],
[style*="overflow-x"] * { touch-action: pan-x pan-y !important; }

/* เว็บที่มีคลาส — ระบุคลาสตรง ๆ ชัดกว่า */
.chip-row, .table-scroll, .map { touch-action: pan-x pan-y !important; }
```

🔑 **ตัวจับจากสไตล์มีข้อดีคือครอบของที่เพิ่มทีหลังให้เอง** — กล่องไหนตั้งให้เลื่อนข้างได้
= ตั้งใจให้เลื่อนอยู่แล้ว จึงยกเว้นถูกเสมอ **ไม่ต้องกลับมาแก้กฎทุกครั้งที่ทำแถบใหม่**

⚠️ `pan-x pan-y` **ยังบีบซูมไม่ได้** (ค่าที่ปล่อยให้ซูมคือ `pinch-zoom` ซึ่งไม่ได้ใส่)

## 🔴 ก่อนขยายปุ่มให้ถึงเกณฑ์ ต้องอ่านคอมเมนต์ในไฟล์ก่อน

**บางปุ่มเล็กเพราะพี่กันสั่งเอง** ไม่ใช่เพราะยังไม่ได้แก้
🚨 **ขยายทับของที่พี่กันเคาะแล้ว = ทำในสิ่งที่ถูกสั่งห้ามไว้แล้ว** อ่านคอมเมนต์ก่อนเสมอ

## ⌨️ แป้นพิมพ์บนมือถือ — ต้องกัน 3 ชั้น (ข้อ 3)

> **อาการ** กดช่องกรอกในป๊อปที่ตรึงขอบล่าง **แป้นพิมพ์เด้งขึ้นมาทับปุ่มยืนยันจนกดไม่ได้**
> ผู้ใช้พิมพ์เสร็จแล้วไปต่อไม่ได้ ต้องปิดแป้นพิมพ์เองก่อน ซึ่งหลายคนไม่รู้ว่าต้องทำ

**ชั้นที่ 1 · บอกเบราว์เซอร์ให้หดพื้นที่เนื้อหา**

```js
export const viewport = { interactiveWidget: 'resizes-content' };
```

**ชั้นที่ 2 · วัดความสูงแป้นพิมพ์เอง แล้วส่งเป็นตัวแปรให้ CSS ใช้**

🚨 **ต้องมีชั้นนี้เสมอ ชั้นที่ 1 อย่างเดียวไม่พอ** — บาง iOS ไม่หดพื้นที่ให้แม้ตั้งค่าแล้ว

```js
const vv = window.visualViewport;
const วัด = () => {
  const gap = Math.max(0, window.innerHeight - vv.height - vv.offsetTop);
  document.documentElement.style.setProperty('--kb', Math.round(gap) + 'px');
};
vv.addEventListener('resize', วัด);
vv.addEventListener('scroll', วัด);
```

**ชั้นที่ 3 · ป๊อปดันตัวเองขึ้นเท่าความสูงแป้นพิมพ์**

```css
:root { --kb: 0px; }                              /* 🚨 ต้องตั้งค่าตั้งต้นไว้ก่อนเสมอ */
.sheet { transform: translateY(calc(var(--kb) * -1)); transition: transform .18s ease; }
```

🚨 **ขาด `:root { --kb: 0px }` แล้ว `calc(var(--kb) * -1)` พังทั้งบรรทัด** ตอนที่ยังไม่มีแป้นพิมพ์
CSS ที่คำนวณไม่ได้จะถูกทิ้งทั้งประโยค ป๊อปจึงไม่ขยับเลยแม้แต่ตอนมีแป้นพิมพ์

🚨 **ปุ่มยืนยันต้องอยู่ในกล่องที่ดันขึ้น ไม่ใช่ตรึงกับขอบจอแยกต่างหาก**
ถ้าตรึงแยก มันยึดกับขอบจอซึ่งอยู่ใต้แป้นพิมพ์ ดันยังไงก็ไม่โผล่

## 📄 ป๊อปบนมือถือ — เลื่อนขึ้นจากขอบล่าง (ข้อ 10)

> **ป๊อปเด้งกลางจอ = รู้สึกเป็นเว็บ · แอปจริงเลื่อนขึ้นจากขอบล่าง**
> เพราะนิ้วโป้งอยู่ล่างจอ ของที่โผล่จากตรงนั้นกดต่อได้ทันทีโดยไม่ต้องเอื้อม

```css
.sheet-wrap { position: fixed; inset: 0; display: flex; align-items: flex-end; }
.sheet {
  width: 100%;
  max-height: 88dvh;                    /* 🚨 dvh ไม่ใช่ vh — vh ไม่หดตามแถบเบราว์เซอร์ */
  border-radius: 20px 20px 0 0;
  animation: slideUp .42s cubic-bezier(.16, 1.16, .3, 1) both;
}
@keyframes slideUp { from { transform: translateY(110%) } to { transform: none } }
```

🔑 **`1.16` ที่เกิน 1 ในเส้นจังหวะ = เลยจุดหมายนิดหนึ่งแล้วเด้งกลับ** — ทำให้รู้สึกมีน้ำหนัก
ไม่ใช่แค่ไถลขึ้นมาเฉย ๆ · **`110%` ไม่ใช่ `100%`** เพื่อให้เงาของกล่องพ้นขอบจอไปด้วยตอนเริ่ม

🚨 **จังหวะต้องอยู่ที่ตัวกล่อง ไม่ใช่ที่ฉากซ้อน**
ฉากซ้อนต้องว่างไว้ให้ตัวดันตามแป้นพิมพ์ (ชั้นที่ 3 ของหัวข้อก่อนหน้า) ใช้
ถ้าใส่จังหวะที่ฉากซ้อน ทั้งสองตัวจะแย่ง `transform` กันจนป๊อปกระตุก

### 🔑 กฎที่ตรงข้ามกับความเชื่อทั่วไป

| ป๊อปแบบไหน | กดฉากหลังปิดได้ไหม |
|---|---|
| **ป๊อปที่ต้องพิมพ์** (ค้นหา · กรอกข้อมูล) | **🚨 ห้ามปิด — ต้องมีปุ่ม ✕ แทน** |
| ป๊อปที่แค่กดเลือก (ตัวกรองที่ไม่มีช่องพิมพ์) | ปิดได้ |

**เหตุผล** — พอแป้นพิมพ์เด้งขึ้นมา มันบังปุ่มปิดกับปุ่มยืนยันจนหมด
**ฉากหลังกลายเป็นที่เดียวที่นิ้วกดโดน** ผู้ใช้ที่กะจะกดปุ่มแล้วพลาดไปโดนฉากหลัง
= ป๊อปปิดทันที ของที่พิมพ์ไปหายหมด

## 🔴 `overflow-x: hidden` ยังเลื่อนด้วยโปรแกรมได้ — ต้องใช้ `clip` (ข้อ 5)

`hidden` **ยังสร้างกล่องเลื่อนอยู่** แค่ซ่อนแถบเลื่อนไว้ — โค้ดยังตั้ง `scrollLeft` ได้
และเบราว์เซอร์ยังเลื่อนให้เองได้ตอนโฟกัสไปโดนของที่อยู่นอกกรอบ

```css
html, body { overflow-x: clip; }   /* ✅ ตัดทิ้งจริง ไม่มีกล่องเลื่อน */
```

🚨 **`clip` ไม่มีผลกับเรื่องหน้าไถลบนมือถือ** (ดูหัวข้อหน้าไถล — ต้องดีดตำแหน่งกลับด้วย JS)
แต่กันเคสที่ **โฟกัสกระโดดไปช่องที่อยู่นอกจอแล้วหน้าเลื่อนตามเอง** ได้จริง

⚠️ ใช้ `clip` แล้วลูกที่ตั้ง `position: sticky` ในแกนนั้นจะไม่ทำงาน — ถ้ามี ให้ใช้ `hidden` เฉพาะกล่องนั้น

## 🔴 ข้อความใบ้ในช่องกรอก วรรณยุกต์โดนตัด (ข้อ 1)

**กลไกที่ 4 ของเรื่องวรรณยุกต์ไทย** — สามกลไกแรกอยู่ในสกิล `form-input` กับ `search-system`

```css
input::placeholder, textarea::placeholder { line-height: inherit !important; }
```

🚨 **`::placeholder` สืบทอด "ฟอนต์" จากช่องกรอก แต่ไม่สืบทอด `line-height`**
มันกลับไปใช้ค่า `normal` ของเบราว์เซอร์ ซึ่งไม่พอสำหรับวรรณยุกต์ไทย

**อาการ** — ช่องที่ยังไม่ได้พิมพ์อะไร ข้อความสีเทาที่บอกว่าให้กรอกอะไร **โดนตัดหัววรรณยุกต์**
พอพิมพ์แล้วตัวอักษรจริงกลับปกติ · **จับได้ยากมากเพราะต้องดูตอนช่องยังว่างเท่านั้น**

## 🔴 ตัวป้องกันทุกตัวต้องผูกให้เร็วที่สุด (ข้อ 11 · ขยายจากหัวข้อด้านบน)

หัวข้อ "การป้องกันที่ผูกกับคลาสซึ่งใส่ตอนวางจอเสร็จ" บอกไว้แล้วว่าอย่าผูกกับคลาส
**ข้อนี้บอกต่อว่าแล้วต้องผูกที่ไหนแทน**

| โครงเว็บ | ผูกที่ไหน |
|---|---|
| React แบบคลาส | **`constructor`** + ธง `_earlyBound` กันผูกซ้ำ (โหมดเข้มงวดสร้างสองรอบ) |
| React แบบฟังก์ชัน / Next.js | **สคริปต์ฝังในหน้า** (`<script dangerouslySetInnerHTML>` ต้น `<body>`) |

🚨 **ห้ามผูกใน `useEffect` หรือ `componentDidMount`** — บนมือถือช่วงตั้งแต่หน้าโหลด
จนส่วนประกอบวางเสร็จกินเวลา **หลายวินาที** ผู้ใช้แตะจอได้แล้วแต่ยังไม่มีอะไรกัน
ซูมทีเดียวหรือลากทีเดียวก็ค้างอยู่อย่างนั้นทั้งรอบ

🚨 **สคริปต์ฝังในหน้าเร็วกว่า constructor อีก** เพราะทำงานตั้งแต่ตอนอ่าน HTML
ยังไม่ต้องรอโค้ดของเว็บโหลดเสร็จด้วยซ้ำ

## 🔴 ดึงลงเพื่อโหลดใหม่ — 4 อย่างที่ขาดไม่ได้ (ข้อ 16 · เติมจากหัวข้อด้านบน)

| ต้องทำ | ถ้าไม่ทำ |
|---|---|
| แถบต้อง `height: 0; overflow: visible` แล้วให้กล่องในเป็น `absolute` | **แถบดันเนื้อหาลงตลอดเวลา** ทั้งที่ยังไม่ได้ดึง |
| ขยับด้วย `transform: translateY()` **ห้ามใช้ `margin` / `padding`** | เบราว์เซอร์คำนวณผังใหม่ทุกเฟรม = กระตุก |
| `overflow-anchor: none` ที่พื้นที่เลื่อน | ระบบยึดตำแหน่งของเบราว์เซอร์สู้กับตัวเราจนภาพสั่น |
| เก็บค่าใหม่เฉพาะเมื่อ**ต่างจากเดิมเกิน 1px** | วาดหน้าใหม่ทุกเฟรมที่นิ้วขยับ |

## 🔴 ล็อกความกว้างของแอปเท่าขอบจอจริง (ข้อ 4 · ชั้นเสริมของหัวข้อหน้าไถล)

ตารางในหัวข้อ "หน้าไถลซ้ายขวา" บอกว่าท่านี้ **"ล็อกได้จริง แต่ยังลากได้"**
จึงเป็น**ชั้นเสริม** ไม่ใช่ตัวแก้หลัก (ตัวหลักคือดีดตำแหน่งกลับ 0)

```js
const lockWidth = () => {
  const vv = window.visualViewport;
  const w = Math.floor(Math.min(vv ? vv.width : Infinity, window.innerWidth,
                                document.documentElement.clientWidth));
  document.documentElement.style.setProperty('--app-w', w + 'px');
};
window.visualViewport?.addEventListener('resize', lockWidth);
window.visualViewport?.addEventListener('scroll', lockWidth);
```

🚨 **ต้องปัดลงเสมอ (`Math.floor`)** — เกินครึ่งจุดภาพก็ลากได้แล้ว
🚨 **ต้องผูกทั้ง `resize` และ `scroll` ของกรอบที่ตาเห็น** ไม่ใช่แค่ `resize` ของหน้าต่าง
🔑 **ทำไมต้องถามเครื่อง ไม่ใช้ `100vw`** — `100vw` นับรวมแถบเลื่อนและอิงกรอบผัง
ซึ่งบนไอโฟนกว้างกว่าขอบจอจริงเมื่อมีอะไรล้นแม้ครั้งเดียว
